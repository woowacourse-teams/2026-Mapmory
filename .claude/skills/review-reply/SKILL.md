PR #$ARGUMENTS 의 리뷰 지적을 처리한다.

원칙: 고치기 전에 검증하고, 짐작하기 전에 묻는다. 분위기보다 기술적으로 맞는지가 먼저다.
리뷰도 틀릴 수 있다. 지적을 다 따르면 불필요한 코드가 쌓이고, 리뷰가 맞았는지도 알 수 없게 된다.
(obra/superpowers의 `receiving-code-review`를 우리 흐름에 맞게 옮겼다.)

## 1. 모으기

- `gh api --paginate repos/{owner}/{repo}/pulls/$ARGUMENTS/comments`(코멘트가 30개를 넘을 수 있어 모든 페이지를 읽는다)에서
  `github-actions[bot]`이 단 코멘트 중 `in_reply_to_id`가 없고 아직 답글이 없는 것을 모은다.
- 요약 코멘트(`gh pr view $ARGUMENTS --comments`)의 "팀 결정 필요"도 함께 본다.

## 2. 검증하기 (아직 코드를 고치지 않는다)

AI 리뷰어는 이 PR의 맥락을 다 알지 못하는 외부 리뷰어로 대한다. 회의적으로 보되 꼼꼼히 확인한다.

1. 지적을 끝까지 읽고, 무엇을 요구하는지 한 문장으로 다시 쓴다. 다시 쓸 수 없을 만큼 불분명하면 그 지적은 "질문"으로 둔다.
2. 지적이 말한 입력이나 실행 순서를 실제 코드에서 따라간다. 가능하면 그 상황을 재현하는 테스트를 써서 고치기 전 코드에서 실패하는지 본다.
3. 아래 중 하나라도 해당하면 반박 후보다.
   - 고치면 기존 동작이 깨진다.
   - 리뷰가 맥락을 모른다(지금 구현의 이유, PR 설명의 "결정", ADR).
   - 쓰이지 않는 기능을 더하라는 제안이다. 코드에서 실제 사용처를 찾아보고, 없으면 반박하거나 사람에게 뺄지 묻는다.
   - 우리 스택(Spring, MySQL/InnoDB, JPA)에서 기술적으로 틀렸다.
   - 사람이 정한 결정과 부딪힌다. 이때는 반박하지 말고 "판단 필요"로 사람에게 넘긴다.
4. 판단을 넷 중 하나로 정한다.
   - **재현됨:** 지적이 맞다. 고칠 방법을 적는다.
   - **재현 안 됨:** 지적이 틀렸다. 코드 위치와 근거(테스트 결과, 문서 링크)를 적는다.
   - **판단 필요:** 동작은 맞지만 무엇·왜의 문제다(정책, API 계약, 결정과 충돌). 사람에게 넘긴다.
   - **질문:** 무엇을 요구하는지 불분명하다.

## 3. 보여 주고 멈추기

표로 보여 준다: 지적, 판단, 근거, 할 일. 사람이 판단을 고칠 수 있게 한다.
"질문"이 하나라도 있으면 다른 것도 고치지 않는다. 지적끼리 얽혀 있을 수 있어, 일부만 이해한 채 고치면 틀린다. 먼저 묻는다.

## 4. 사람이 승인하면

- 고치는 순서: 막는 문제(깨짐, 보안) → 단순한 것 → 복잡한 것(로직, 구조). 하나 고칠 때마다 테스트를 돌려 회귀가 없는지 본다.
- 답글은 각 코멘트의 스레드에 단다: `gh api repos/{owner}/{repo}/pulls/$ARGUMENTS/comments/<코멘트 id>/replies -f body=...`
- 답글은 판단부터 쓰고 짧게 쓴다.
  - 재현됨: "재현됨. [무엇을 확인했나]. [커밋]에서 [무엇을] 고쳤다."
  - 재현 안 됨: "재현 안 됨. [코드 위치]에서 [이유]. [테스트·문서 근거]."
  - 판단 필요·질문: 사람이 정한 내용이나 질문을 그대로 쓴다.
- 쓰지 않는 말: "맞습니다", "좋은 지적입니다", "감사합니다" 같은 동의·감사 표현. 확인한 근거 없이 동의하면 리뷰가 맞았는지 알 수 없다.
- 반박이 틀렸던 것으로 드러나면 사실만 짧게 고쳐 적고 넘어간다.

## 5. 하지 않는 것

리뷰 코멘트에 👍/👎 반응은 달지 않는다. 리뷰 정확도를 재는 사람의 판정이다. 끝나면 사람에게 지적마다 👍/👎를 달아 달라고 말한다.
