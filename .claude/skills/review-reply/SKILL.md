PR #$ARGUMENTS 의 리뷰 지적을 처리한다. 리뷰도 틀릴 수 있다. 지적을 다 따르면 불필요한 코드가 쌓이고, 리뷰가 맞았는지도 알 수 없게 된다.

1. 지적을 모은다: `gh api --paginate repos/{owner}/{repo}/pulls/$ARGUMENTS/comments`(코멘트가 30개를 넘을 수 있어 모든 페이지를 읽는다)에서 `github-actions[bot]`이 단 코멘트 중 `in_reply_to_id`가 없고 아직 답글이 없는 것. 요약 코멘트(`gh pr view $ARGUMENTS --comments`)의 "팀 결정 필요"도 함께 본다.
2. 지적마다 확인한다. 코드를 고치기 전에 판단부터 한다.
   - 지적이 말한 입력이나 실행 순서를 실제 코드에서 따라간다. 가능하면 그 상황을 재현하는 테스트를 써서 고치기 전 코드에서 실패하는지 본다.
   - 판단을 셋 중 하나로 정한다.
     - **재현됨:** 지적이 맞다. 고칠 방법을 적는다.
     - **재현 안 됨:** 지적이 틀렸다. 왜 그 결과가 나오지 않는지 코드 위치와 근거(테스트 결과, 문서 링크)를 적는다.
     - **판단 필요:** 동작은 맞지만 무엇·왜의 문제다(정책, API 계약). 사람에게 넘긴다.
3. 표로 보여 주고 멈춘다: 지적, 판단, 근거, 할 일. 사람이 판단을 고칠 수 있게 한다.
4. 사람이 승인하면
   - "재현됨"은 고치고 테스트를 돌린 뒤, 답글에 고친 커밋과 테스트 결과를 적는다.
   - "재현 안 됨"은 고치지 않고, 답글에 근거를 적는다.
   - 답글은 `gh api repos/{owner}/{repo}/pulls/$ARGUMENTS/comments/<코멘트 id>/replies -f body=...`로 단다.
5. 리뷰 코멘트에 👍/👎 반응은 달지 않는다. 리뷰 정확도를 재는 사람의 판정이다. 끝나면 사람에게 지적마다 👍/👎를 달아 달라고 말한다.
