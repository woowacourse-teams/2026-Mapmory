# ADR 0009. Region 지도 요약 API와 테스트 범위

- 상태: 채택
- 날짜: 2026-08-11
- 관련: ADR 0004, ADR 0008, 이슈 #24, #25, #26

---

## 문제

국가, 시도, 시군구마다 별도 요청 파라미터를 추가하면 Region 계층이 늘어날 때마다 API 계약이 변경된다. 반면 `region_code`는 국가별로 중복될 수 있으므로 코드 하나만으로 Region을 식별할 수 없다.

지역 탐색은 별도의 Region API가 담당하므로 지도 요약 API가 기록이 없는 Region까지 반환할 필요는 없다. 클라이언트는 지도 요약 응답에 없는 Region을 색칠 단계 0으로 처리할 수 있다.

## 결정

지도 요약 API는 Region 계층을 기준으로 구성한다.

- `GET /api/v1/travel-records/map-summary/regions/roots`는 기록이 있는 국가 Region의 요약을 반환한다.
- `GET /api/v1/travel-records/map-summary/regions/{regionId}/children`은 특정 Region의 기록이 있는 직속 자식 요약을 반환한다.
- 응답은 후속 요청용 `regionId`와 로컬 지도 매칭용 `code`를 함께 제공한다.
- 클라이언트는 `regionId`를 행정 코드처럼 영구 저장하지 않고 API 탐색에만 사용한다.
- 기록이 없는 Region은 응답에서 제외하고 클라이언트가 `count = 0`, `level = NONE`으로 처리한다.
- 색상 단계는 의미가 드러나는 `NONE`, `LOW`, `MEDIUM`, `HIGH` 문자열로 표현한다.
- 각 결과 Region은 자신과 모든 하위 Region의 기록을 포함한다.

## 조회 방식

부모 ID가 없으면 루트 Region을, 있으면 해당 Region의 직속 자식을 반환 대상으로 구성한다. 현재 회원의 기록 Region에서 `id`, `parent_id`, `root_id`를 이용해 반환 대상 Region으로 상향 집계한 뒤 기록이 집계된 대상만 반환한다. 고정된 3단계 계층을 활용하므로 전체 Region 트리를 재귀 탐색하지 않는다. 엔티티 그래프를 순회하지 않고 스칼라 프로젝션을 반환해 N+1 쿼리를 방지한다.

## 테스트 범위

- 색상 단계 정책은 Spring 없이 단위 테스트한다.
- 서비스는 Repository를 대역으로 둔 단위 테스트로 회원 검증과 응답 변환을 확인한다.
- 컨트롤러는 MVC 슬라이스 테스트로 HTTP 계약을 확인한다.
- Repository 쿼리와 Flyway 스키마의 호환성만 MySQL Testcontainers 통합 테스트로 확인한다.
- 서비스 전체 Spring 통합 테스트는 같은 동작을 중복 검증하고 실행 비용이 크므로 작성하지 않는다.

## 결과

- Region 단계가 추가돼도 계층별 파라미터를 새로 만들 필요가 없다.
- 중복 가능한 행정 코드가 API 조회 식별자로 단독 사용되지 않는다.
- 지도 코드와 DB 식별자의 역할이 분리된다.
- 기록이 없는 Region을 전송하지 않아 지도 요약 응답 크기가 줄어든다.
- 운영 MySQL과 같은 DB에서 집계 쿼리를 검증하면서도 대부분의 테스트는 빠르게 유지한다.

## 보완: 화면 단위 전체 조회 (2026-11-10, #656)

지도 화면은 국가, 시도, 시군구를 모두 그린다. 계층 API만 있으면 앱이 "루트 → 대한민국 하위 → 기록 있는 시도마다 하위"를 차례로 불러야 한다. 그래서 요청이 `2 + 기록 있는 시도 수`번 나가고, 앞 응답을 기다리는 동안 왕복 시간이 쌓인다.

- `GET /api/v1/travel-records/map-summary`를 더한다. 기록이 있는 모든 단계의 Region을 한 목록으로 주고, 항목마다 `parentRegionId`를 담는다. 국가는 `null`이다.
- 세는 규칙, 색상 단계, `tagId` 필터는 계층 API와 같다. 쿼리 한 번으로 센다.
  - 먼저 회원 기록을 저장된 지역별로 센다. 그 수를 자기 지역, `parent_id`, `root_id`에 더한다.
  - region과 `id OR parent_id OR root_id`로 조인하면 MySQL 8.4가 조건 없는 해시 조인을 고른다. 기록 5,000건에서 248만 줄을 만들어 261ms가 걸렸다. 지역별로 먼저 세는 방식으로 바꾸니 10ms였다(로컬 Testcontainers, 30회 중앙값).
  - 이 실행 계획은 리포지토리 테스트가 지킨다.
- 시군구는 시도를 누를 때 받는 방식(B)도 검토했지만, 화면을 그릴 때 한 번에 받는다(A).
  - 지금 앱도 진입할 때 기록 있는 시도의 하위를 미리 받고 있다. A는 이 요청들을 하나로 묶는 것이다.
  - B로 하려면 국가·시도를 한 번에 주는 API가 따로 필요하다. 그러면 진입 1번에, 시도를 누를 때마다 1번씩 더 왕복한다.
  - B가 아끼는 것은 시군구 줄뿐이다. 응답은 기록이 있는 지역만 담아 보통 수십 줄이고, 최악이어도 지역 수(현재 496개)를 넘지 않는다. 반면 누를 때마다 기다리는 시간은 사용자에게 바로 보인다.
  - A는 한 시점의 결과라 국가·시도·시군구 수가 항상 맞는다. B는 진입과 클릭 사이에 기록이 바뀌면 어긋날 수 있다.
  - 해외 시도·시군구 데이터가 추가돼 응답이 수천 줄 규모가 되면 B를 다시 검토한다.
- 계층 API는 남긴다. 옛 앱이 계속 쓰기 때문이다.
- 캐시는 계층 API와 같은 회원 단위 캐시를 쓰되, 루트 조회와 키가 겹치지 않게 범위를 나눈다.
- 집계 테이블은 만들지 않는다. 운영 `MAP_SUMMARY_QUERY` 측정값을 본 뒤에 다시 판단한다.
