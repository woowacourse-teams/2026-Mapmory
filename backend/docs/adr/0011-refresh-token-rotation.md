# ADR 0011. refresh 토큰은 해시 저장·회전·폐기하고, 재사용을 감지한다

- 상태: 채택
- 날짜: 2026-08-14
- 관련: #47, ADR 0009

---

## 문제

access token은 단기(30분)라 자주 만료된다. 사용자가 매번 카카오 로그인을 다시 하지 않도록
장기 세션 수단이 필요하다. 동시에, 장기 토큰은 탈취 시 위험이 크므로 서버가 이를
폐기·회전할 수 있어야 한다.

## 결정

### refresh 토큰의 원문은 클라이언트에만, 서버는 해시만 저장한다

- 원문은 `SecureRandom` 32바이트를 Base64URL로 인코딩한 불투명 문자열이다.
- 서버는 원문을 저장하지 않고 **SHA-256 해시(64 hex)만** DB에 보관한다.
  DB가 유출되어도 저장된 해시로는 원문을 만들 수 없다.
- 조회는 들어온 원문을 같은 방식으로 해시해 대조한다.

### 사용 시 회전(rotation)한다

`POST /api/v1/auth/token/refresh`로 재발급할 때, 기존 refresh를 폐기(`revoked_at` 기록)하고
새 access/refresh 쌍을 발급한다. 하나의 refresh는 한 번만 유효하다.

### 서버가 폐기할 수 있다

`POST /api/v1/auth/logout`으로 refresh를 폐기한다. 만료·폐기·위조된 refresh로 재발급을
시도하면 401로 응답한다.

### 회전은 원자적으로 처리하고, 재사용은 탈취로 간주해 대응한다

같은 토큰으로 동시 요청이 와도 한 번만 회전되도록, 검증 시 토큰 행에 비관적 락
(`SELECT ... FOR UPDATE`)을 건다. 이미 폐기된 refresh가 다시 제시되면 정상 사용자와
탈취자가 같은 원문을 나눠 가진 상황이므로 해당 회원의 유효한 refresh를 **모두 폐기**한다.

이 일괄 폐기는 검증과 **같은 트랜잭션**에서 수행하고, 재사용일 때는 예외를 던지지 않고
결과로 신호한다(`Optional.empty`). 401 변환은 트랜잭션 밖(호출부)에서 하므로 폐기가
롤백되지 않는다. (초기엔 `REQUIRES_NEW` 별도 트랜잭션을 썼으나, 비관적 락과 결합 시
같은 회원 행을 두 트랜잭션이 서로 기다리는 **데드락**이 생겨 같은 트랜잭션 방식으로 바꿨다.)

만료는 14일(`jwt.refresh-token-validity`)로 둔다.

## 검토한 대안

### refresh도 stateless JWT로 발급

채택하지 않았다. 구현은 단순하지만 서버가 특정 refresh를 폐기할 수 없어,
로그아웃·탈취 대응이 불가능하다. 폐기 가능성이 이 결정의 핵심 목적이다.

## 결과

### 장점

- 재로그인 없이 세션을 유지하면서, 서버가 언제든 refresh를 폐기할 수 있다.
- 원문을 저장하지 않아 DB 유출 시 토큰이 그대로 노출되지 않는다.
- 회전 + 재사용 감지로 탈취된 토큰의 수명을 제한한다.

### 비용과 주의점

- 매 재발급마다 DB 조회·쓰기가 발생한다(무상태 access와 달리 상태를 가짐).
- 만료·폐기된 토큰 정리(purge) 배치는 후속 과제다.
- 회전 검증이 비관적 락을 쓰므로, 같은 토큰에 동시 요청이 몰리면 잠깐 직렬화된다.
