# ADR 0013. 사용자 생성 태그와 여행 기록의 연결을 별도 연관 엔티티로 관리한다

- 상태: 채택
- 날짜: 2026-08-21
- 관련: ADR 0009, `api.md`, `backend/docs/erd.md`

---

## 문제

사용자는 `연인`, `친구`, `가족`, `라멘 맛집`처럼 자신에게 의미 있는 태그를 만들고,
여행 기록에 연결해 기록 목록과 지도 영역을 필터링하고 싶다. 미리 정한 태그 목록만
제공하면 사용자의 분류 방식을 충분히 표현할 수 없다.

태그는 회원마다 독립적으로 관리되어야 하며, 다른 회원의 태그를 기록에 연결하거나
조회 조건으로 사용할 수 없어야 한다. 이름 비교에서는 불필요한 공백과 대소문자 차이를
중복으로 취급하면서도 화면에는 사용자가 입력한 대소문자를 보존해야 한다.

기록과 태그는 다대다 관계이지만, JPA 매핑의 간결함만을 기준으로 결정하면 소유권 검증,
연결 개수 제한, 조회 인덱스와 이후 연결 메타데이터 확장이 서비스 밖으로 흩어질 수 있다.

## 결정

### 태그는 회원이 직접 생성하고 회원 범위에서 관리한다

- `tag`는 `member_id`, 화면 표시용 `name`, 중복 비교용 `name_key`를 가진다.
- 같은 회원 안에서 `name_key`는 유일하고, 다른 회원은 같은 이름을 사용할 수 있다.
- 회원당 최대 10개는 MVP의 **임시 제한**이다. 실제 사용량과 UI 요구를 측정한 뒤 조정한다.
- MVP의 기록 목록과 지도 요약은 한 번에 하나의 `tagId`로 필터링한다.

### 이름 정규화와 검증은 Tag 도메인의 생성·변경 경로에서 수행한다

`Tag.of`와 `Tag.rename`은 원본 문자열을 그대로 저장하지 않고 다음 순서로 처리한다.

1. 앞뒤 공백을 제거한다.
2. 연속된 공백을 하나로 줄인다.
3. Unicode NFC로 정규화한다.
4. 길이와 금지 문자를 검증한다.
5. 표시 이름은 대소문자를 보존하고, `Locale.ROOT` 소문자 변환 결과를 `name_key`로 만든다.

현재 `#`과 제어 문자를 허용하지 않는다. `#` 제한은 태그 표시 규칙을 단순하게 유지하기
위한 제품 규칙이지 SQL Injection 방어 수단이 아니다. 데이터베이스 입력은 JPA의 바인딩
파라미터로 처리하며, 보안과 이름 정책을 분리한다.

### 기록과 태그의 연결은 TravelRecordTag 연관 엔티티로 표현한다

`travel_record`가 `List<Tag>`를 직접 소유하는 대신 `travel_record_tag`와
`TravelRecordTagService`가 연결을 관리한다.

- 서비스는 요청 태그가 모두 현재 회원 소유인지 한 번에 조회해 검증한다.
- 기록당 최대 5개는 MVP의 **임시 제한**이다.
- 중복된 태그 ID 요청을 거부한다.
- 기록 생성·수정 트랜잭션 안에서 검증과 연결 저장을 수행한다.
- 목록 응답을 위한 일괄 조회와 태그별 기록·지도 조회를 명시적인 Repository 쿼리로 제공한다.

연결 자체가 엔티티이므로 이후 정렬 순서, 별칭, 연결한 시각 같은 속성이 필요해져도
`travel_record`와 `tag`의 생명주기를 바꾸지 않고 확장할 수 있다.

### 연관 엔티티는 단일 PK와 태그 선두 UNIQUE를 사용한다

- `travel_record_tag.id`를 AUTO_INCREMENT PK로 사용해 JPA 식별과 Repository 타입을 단순하게 유지한다.
- `(tag_id, travel_record_id)` UNIQUE로 동일한 연결의 중복을 차단한다.
- 이 UNIQUE 인덱스는 태그별 기록 조회에서 사용할 수 있고, 두 ID만 필요한 경우 커버링 인덱스가 된다.
- MySQL InnoDB는 `travel_record_id`로 시작하는 인덱스가 없으면 외래 키 인덱스를 자동 생성한다.
- 회원별 태그가 최대 10개이므로 `created_at` 정렬 전용 인덱스는 두지 않는다.
- 추가 커버링 인덱스는 실제 데이터와 쿼리 실행 계획을 측정한 뒤 도입한다.

### 기록의 태그 변경은 기존 연결을 삭제한 뒤 다시 생성한다

기록당 연결이 최대 5개이고 연결에 수정할 속성이 없는 현재 단계에서는 차이를 계산해
개별 추가·삭제하는 것보다 전체 삭제 후 재생성이 규칙을 이해하고 검증하기 쉽다. 삭제 쿼리를
실행한 뒤 `flush`하여 UNIQUE 충돌 가능성을 없애고 새 연결을 저장한다.

연결에 보존해야 할 메타데이터가 추가되거나 쓰기 비용이 측정상 문제가 되면 차이 갱신으로
변경한다.

### 별도 Tags·MemberTags aggregate는 지금 도입하지 않는다

현재 회원 단위 규칙은 태그 개수 제한과 이름 중복 검증뿐이며 `TagService`에서 충분히
드러난다. 컬렉션 전체를 불러오는 aggregate를 만들면 단순한 CRUD에도 추가 객체와 조회가
필요하다. 태그 간 순서, 일괄 변경, 조합 규칙처럼 컬렉션 자체의 행위가 생길 때 다시 검토한다.

### 마이그레이션은 태그와 연결 테이블을 분리한다

V15가 적용된 환경이 없으므로 V15는 `tag`만 생성하도록 정리하고, `travel_record_tag`는
V16에서 생성한다. 사용자 태그와 기록 연결이라는 두 리뷰 단위를 스키마에서도 분리한다.

## 검토한 대안

### TravelRecord가 `List<Tag>`를 직접 가지는 JPA `@ManyToMany`

매핑 코드는 짧아지지만 연결 개수와 회원 소유권 검증의 책임이 불명확해지고, 연결 테이블의
쿼리·인덱스·추가 속성을 제어하기 어렵다. 연결을 독립적인 개념으로 다뤄야 하므로 채택하지 않았다.

### `(travel_record_id, tag_id)` 복합 PK

DB 식별자는 자연스럽지만 JPA에서 복합 ID 클래스와 `@MapsId`, 동등성 구현이 필요해 코드가
복잡해진다. 중복 방지는 UNIQUE로 충분하므로 단일 PK를 선택했다.

### 정규화된 이름 하나만 저장

스키마는 단순하지만 사용자가 입력한 `RAMEN PLACE` 같은 표현을 보존할 수 없다. 표시와 비교의
역할을 `name`, `name_key`로 분리했다.

### 모든 변경을 차이 계산으로 갱신

불필요한 DELETE와 INSERT를 줄이고 연결 ID·생성 시각을 보존할 수 있다. 하지만 최대 5개 연결에
집합 비교와 분기 로직이 추가된다. 보존할 연결 속성이 없는 현재는 단순한 재생성을 선택했다.

### 예상 조회를 기준으로 명시 인덱스를 먼저 추가

일부 쿼리는 빨라질 수 있지만 데이터 분포와 실행 계획 없이 추가하면 쓰기 비용과 저장 공간만
늘거나 옵티마이저가 사용하지 않을 수 있다. PK·UNIQUE·FK가 제공하는 인덱스로 시작하고 측정 후
추가한다.

## 결과

### 장점

- 태그 이름과 연결 규칙을 생성·수정 경로에서 일관되게 보장한다.
- 회원 소유권과 임시 개수 제한이 서비스 흐름에 명시적으로 드러난다.
- 태그별 기록 목록과 지도 집계에 필요한 관계를 직접 조회할 수 있다.
- JPA 식별 구조를 단순하게 유지하면서 DB UNIQUE로 중복 연결을 방지한다.
- 이후 연결 속성이나 컬렉션 규칙이 생길 때 확장 지점이 분명하다.

### 비용과 주의점

- `TravelRecord`에서 태그를 바로 탐색할 수 없어 서비스와 Repository 코드가 늘어난다.
- 전체 재생성 시 기존 연결 ID와 `created_at`이 유지되지 않고 DELETE·INSERT가 발생한다.
- `name`과 `name_key`의 일관성을 애플리케이션 생성·변경 경로가 책임진다.
- 10개·5개 제한과 단일 태그 필터는 확정 정책이 아니므로 실제 사용 데이터를 기반으로 재검토해야 한다.
- 추가 인덱스는 운영 데이터 규모에서 실행 계획과 응답 시간을 측정한 뒤 별도 결정으로 남긴다.

## 2026-10-28 구현 업데이트: 연결은 차이로 바꾸고 애그리거트가 관리한다

"모든 변경을 차이 계산으로 갱신"을 대안에서 채택으로 바꾼다. 보존할 연결 속성이 없다는 판단은 그대로지만,
이유가 달라졌다. 개수·중복·소유 규칙을 `TravelRecord` 애그리거트로 옮기면서, 그대로 남는 태그를 지웠다 다시 넣으면
Hibernate의 쓰기 순서(INSERT가 DELETE보다 먼저) 때문에 UNIQUE에 걸린다. 그래서 차이로 바꿔야 한다.
태그를 건드리지 않는 수정에서는 연결 쓰기가 없어진다. `TravelRecordTagService`는 없앴다.
실측과 삭제 경로는 ADR 0017의 2026-10-28 보완에 있다.
