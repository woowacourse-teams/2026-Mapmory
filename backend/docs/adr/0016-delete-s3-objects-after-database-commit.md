# ADR 0016. S3 객체는 데이터베이스 커밋 이후 삭제한다

- 상태: 채택
- 날짜: 2026-08-28
- 관련: ADR 0014, 이슈 #162

---

## 문제

Mapmory의 이미지는 앱이 Presigned URL로 S3에 직접 업로드하고, 서버는 S3 객체의 `objectKey`를
`record_media`에 저장한다. 기록 삭제와 수정으로 `record_media` 행이 없어져도 S3 객체는 자동으로
삭제되지 않으므로 다음 경로에서 저장 비용이 계속 누적된다.

1. 이미지가 연결된 기록을 삭제한다.
2. 기록 수정에서 기존 이미지를 제외한다.
3. 이미지를 업로드한 뒤 기록 저장을 취소해 어떤 `record_media`에도 연결하지 않는다.

데이터베이스 트랜잭션과 S3 요청을 하나의 원자적 트랜잭션으로 묶을 수 없으므로, DB 행과 S3 객체 중
무엇을 먼저 삭제할지 결정해야 한다. 또한 운영 버킷은 여러 팀이 함께 사용하고 버전 관리가 꺼져 있어
잘못 삭제한 객체는 복구할 수 없다.

## 결정

### 사용자가 명시적으로 제거한 객체는 즉시 정리한다

- 기록 삭제 시 그 기록에 연결된 모든 `objectKey`를 삭제 대상으로 잡는다.
- 기록 수정 시 기존 키 집합에서 수정 요청에 남은 키 집합을 뺀 결과만 삭제 대상으로 잡는다.
- 유지되거나 순서만 바뀐 객체는 삭제하지 않는다.

업로드 후 기록에 한 번도 연결되지 않은 객체는 기록 수정·삭제 요청이 알 수 없으므로 별도의 대조
작업으로 다룬다.

### 데이터베이스를 먼저 커밋하고 S3를 삭제한다

서비스는 DB 트랜잭션 안에서 삭제할 키 목록을 이벤트로 발행한다. 리스너는
`@TransactionalEventListener(phase = AFTER_COMMIT)`으로 이벤트를 받아 DB 커밋 성공 이후에만
S3 `DeleteObjects`를 호출한다.

```text
기록 수정·삭제
→ DB 변경 및 삭제 대상 이벤트 발행
→ DB 커밋
→ S3 DeleteObjects
```

DB 트랜잭션이 롤백되면 이벤트를 처리하지 않으므로 여전히 사용 중인 이미지를 지우지 않는다.
S3를 먼저 지운 뒤 DB 커밋이 실패해 DB가 삭제된 객체를 참조하는 상태보다, DB 커밋 후 S3 삭제가
실패해 비용만 남는 고아 객체 상태가 복구하기 쉽다고 판단했다.

### S3 삭제 실패는 이미 커밋된 API 결과를 뒤집지 않는다

S3 삭제 실패를 호출자에게 다시 던지면 DB는 이미 커밋됐는데 API만 500으로 보인다. 호출자가 같은
요청을 재시도하면 존재하지 않는 기록을 다시 삭제하거나 이미 반영된 수정을 반복할 수 있다.

따라서 커밋 이후 삭제 예외는 리스너 경계에서 처리한다.

- 구조화 로그 `event=S3_OBJECT_DELETE_FAILED`와 원인 예외를 `ERROR`로 기록한다.
- `mapmory.upload.object.deletion` Counter에 `outcome=SUCCESS|FAILURE`와 대상 객체 수를 기록한다.
- 실패로 남은 객체는 후속 S3·DB 대조 작업이 다시 찾고 정리한다.

현재 리스너는 같은 요청 스레드에서 실행된다. DB 커밋은 S3 응답과 무관하게 확정되지만, HTTP 응답
시간에는 S3 삭제 시간이 포함된다. 삭제 지연이 실제 운영 문제로 확인되면 비동기 실행 또는 영속
Outbox로 전환한다.

### 공유 버킷에서는 Mapmory 경로만 삭제한다

S3 어댑터는 설정된 `keyPrefix` 아래의 `travel-records/` 경로만 허용한다. 운영 설정에서는
`mapmory/travel-records/`가 삭제 가능한 범위다. 범위를 벗어난 키가 하나라도 있으면 S3 요청 자체를
보내지 않는다.

기록 삭제에서는 `RecordMedia` 엔티티를 영속성 컨텍스트에 올리지 않고 `objectKey` 문자열만
조회한다. 자식 엔티티를 로딩한 채 DB의 `ON DELETE CASCADE`로 부모 기록을 지울 때 발생할 수 있는
Hibernate 참조 충돌을 피하기 위해서다.

## 검토한 대안

### S3 객체를 먼저 삭제하고 DB를 변경한다

채택하지 않았다. S3 삭제 뒤 DB 트랜잭션이 롤백되면 DB가 없는 객체를 계속 참조한다. 버전 관리가
꺼진 현재 버킷에서는 삭제된 이미지를 복구할 수도 없다.

### DB 트랜잭션 안에서 S3 삭제를 완료한다

채택하지 않았다. 외부 네트워크 호출 동안 DB 트랜잭션과 커넥션을 오래 점유하며, S3 성공과 DB
커밋 성공을 원자적으로 보장하지도 못한다. S3 장애가 기록 수정·삭제 API 장애로 그대로 확대된다.

### 처음부터 Outbox와 재시도 워커를 도입한다

현재는 채택하지 않았다. 프로세스 종료에도 삭제 요청을 보존할 수 있지만 이벤트 테이블, 상태 전이,
재시도 간격과 워커 운영이 추가된다. 현재 단일 EC2와 이미지 개수에서는 커밋 후 즉시 삭제와 후속
대조 작업의 조합을 먼저 사용한다. 삭제 누락 빈도가 높거나 즉시 삭제 보장이 필요해지면 재검토한다.

### S3 Lifecycle 규칙만 사용한다

채택하지 않았다. S3 Lifecycle은 객체가 `record_media`에서 사용 중인지 알 수 없다. 사용 중 객체와
고아 객체가 같은 prefix에 있으므로 나이만 기준으로 삭제하면 정상 이미지를 지울 수 있다. 미완료
멀티파트 업로드 정리처럼 DB 참조 여부와 무관한 작업에만 Lifecycle을 사용한다.

## 결과

### 장점

- DB 롤백으로 사용 중 이미지가 삭제되는 경로를 차단한다.
- 기록 삭제와 이미지 교체에서 생기는 고아 객체를 즉시 줄인다.
- S3 장애가 이미 커밋된 API 응답을 거짓 실패로 바꾸지 않는다.
- 삭제 실패 건수와 원인을 메트릭·로그로 확인할 수 있다.
- 공유 버킷의 다른 서비스 경로를 삭제하지 못하게 방어한다.

### 비용과 주의점

- DB 커밋과 S3 삭제 사이에 프로세스가 종료되면 이벤트가 유실될 수 있다.
- S3 삭제가 실패하면 객체가 일시적으로 남으며 후속 대조 작업이 필요하다.
- HTTP 응답 시간이 S3 삭제 응답만큼 늘어날 수 있다.
- 업로드 후 기록에 연결되지 않은 객체는 이 흐름으로 발견할 수 없다.
- 버전 관리가 꺼져 있으므로 삭제된 객체는 복구할 수 없다.

## 검증 원칙

- 기록 수정에서는 요청에서 제외한 객체만 삭제한다.
- 기록 삭제에서는 연결된 객체를 모두 삭제한다.
- DB 커밋이 성공한 경우에만 S3 삭제를 실행한다.
- S3 삭제 실패가 기록 수정·삭제의 성공 응답을 바꾸지 않는다.
- 성공·실패 대상 수가 고정된 `outcome` 태그의 메트릭에 기록된다.
- 설정된 Mapmory prefix 밖의 객체는 삭제 요청을 보내지 않는다.
