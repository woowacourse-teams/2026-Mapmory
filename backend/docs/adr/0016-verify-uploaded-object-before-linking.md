# ADR 0016. 기록에 붙는 S3 객체는 저장 시점에 HeadObject로 실존을 확인한다

- 상태: 채택
- 날짜: 2026-08-26
- 관련: ADR 0006, ADR 0014

---

## 문제

이미지는 앱이 presigned URL로 S3에 직접 올린다. 서버는 그 `PUT`을 보지 못하고, 뒤이어 도착한
기록 저장 요청의 `objectKeys` 문자열만 받는다.

```java
// TravelRecordService#create
for (int index = 0; index < objectKeys.size(); index++) {
    RecordMedia recordMedia = RecordMedia.of(savedTravelRecord, objectKeys.get(index), null, index);
    recordMediaRepository.save(recordMedia);   // S3에 실제로 있는지 확인하지 않는다
}
```

즉 **서버는 업로드 성공 여부를 모른 채 키를 저장한다.** `PUT`이 실패했는데 기록 저장만
성공하면 DB에는 키가 있고 S3에는 파일이 없는 상태가 되고, 사용자에게는 영구히 깨진
이미지로 보인다. 서버 로그에는 아무 흔적도 남지 않아 발생 사실조차 알 수 없다.

`S3StorageConfig`에는 `S3Presigner`만 있어 **확인할 수단 자체가 없다.** 현재 검증은
`validateObjectKeysAreAvailable`의 키 중복 체크뿐인데, 이는 "다른 기록이 쓰고 있는가"를
볼 뿐 "존재하는가"와는 무관하다.

이 ADR이 답해야 할 것은 두 가지다. **검증을 할 것인가**, 한다면 **어느 시점에 무엇으로
할 것인가**.

## 현재 업로드 흐름

```
[1] POST /api/v1/uploads/presigned-urls   → 서버가 objectKey + presigned PUT URL 발급 (유효 5분)
[2] PUT  https://{bucket}.s3.../{objectKey} → 앱이 S3로 직행. 서버를 거치지 않는다
[3] POST /api/v1/travel-records            → 앱이 objectKeys 를 본문에 실어 보냄
```

서버가 아는 것은 [1]에서 **무엇을 발급했는지**뿐이고, [2]가 일어났는지는 모른다.
[3]에서 받는 것은 앱의 주장이다.

`objectKey`는 `{keyPrefix}/travel-records/{memberId}/{UUID}.{ext}` 형식이고, 업로드 정책은
파일당 최대 10MB, 요청당 최대 10장이다(`application.yaml`). 기록 하나에 최대 100MB가 붙는다.

## 결정

### 기록 저장 시점에 `headObject`로 실존을 확인한다

`S3StorageConfig`에 `S3Client` 빈을 추가하고, 기록 생성·수정이 `objectKeys`를 저장하기
전에 각 키를 확인한다. 하나라도 없으면 저장 전체를 거절한다.

```
POST /travel-records { objectKeys: [k1, k2] }
        ↓
  headObject(k1), headObject(k2)      ← 서버 ↔ S3, 본문 없는 메타데이터 호출
        ↓ 하나라도 없으면
  400 MEDIA_NOT_UPLOADED
        ↓ 다 있으면
  record_media INSERT
```

부분 저장은 하지 않는다. 10장 중 9장만 붙은 기록은 사용자가 의도한 결과가 아니고,
앱이 어느 장이 빠졌는지 알고 다시 올리게 하는 편이 낫다.

**이 확인이 성립하는 근거는 S3가 read-after-write 강한 일관성을 보장한다는 점이다.**
앱이 `PUT` 200을 받은 뒤 보낸 요청이라면 `headObject`는 반드시 그 객체를 본다.
일관성이 최종적이던 시절이라면 "방금 올렸는데 없다고 나오는" 오탐 때문에 동기 검증
자체가 성립하지 않았을 것이다.

### 확인 실패와 객체 없음을 구분한다

두 상황은 원인도 사용자에게 할 말도 다르다.

| 상황 | `ErrorKind` | 오류 코드 | 의미 |
| --- | --- | --- | --- |
| 객체가 없음 (404) | `INVALID_INPUT` | `MEDIA_NOT_UPLOADED` | 앱이 다시 올리면 해결된다 |
| S3 호출 자체가 실패 | `SERVICE_UNAVAILABLE` | `STORAGE_UNAVAILABLE` | 앱 잘못이 아니다. 잠시 후 재시도 |

S3 장애를 `400`으로 뭉뚱그리면 앱은 "이미지를 다시 올리라"고 안내하게 되는데, 다시 올려도
같은 장애에 걸린다. ADR 0006의 "클라이언트는 안정적인 오류 코드로 분기한다"는 원칙이
여기서 실질적인 차이를 만든다.

기존 `TravelRecordErrorCode.INVALID_OBJECT_KEY`를 재사용하지 않는다. 그 코드의 `detail`은
"중복되거나 다른 여행 일지에서 사용 중"이라 원인을 잘못 지목한다.

### 검증은 upload 패키지가 소유하고, 오류 코드도 `UploadErrorCode`에 둔다

"이 객체가 올라왔는가"는 업로드 도메인의 개념이다. 기록 도메인은 확인을 요청할 뿐
S3도 버킷도 알지 않는다. `TravelRecordService`가 `S3Client`를 직접 들면 기록 도메인이
스토리지 구현에 묶인다.

`PresignedUrlProvider`가 이미 같은 방식으로 S3를 가리고 있고, 그 덕분에
`UploadKeyPrefixIntegrationTest`가 S3 없이 인수 테스트를 돈다. 검증도 같은 형태의
인터페이스로 두어 이 성질을 유지한다.

### 여러 장은 순차로 확인하고, 소요 시간을 계측한다

10장 순차 호출은 같은 리전 기준 100~300ms다. 병렬화는 실행기나 `S3AsyncClient`를
들여야 하는데, 지금 그 복잡도를 살 근거가 없다. `MonitoredOperation`에 항목을 추가해
`OperationTimer`로 재고(ADR 0014), p95가 문제가 되면 그때 병렬로 바꾼다.

### 수정 시 이미 저장된 키는 재검증하지 않는다

`TravelRecordService#update`는 기존 `record_media`와 요청의 `objectKeys`를 대조해 이미
새 키만 골라내고 있다(`validateObjectKeysAreAvailable`). 검증도 같은 대상에만 건다.
이미 붙어 있던 이미지는 저장 시점에 한 번 확인했고, 제목만 고치는 수정에서 사진 10장을
매번 다시 확인할 이유가 없다.

## 검토한 대안

### 서버가 파일을 대신 받아 S3로 넘긴다 (프록시 업로드)

채택하지 않았다. 검증이 공짜로 따라오는 것은 맞다. 서버가 직접 썼으니 성공을 안다.
그러나 **presigned를 쓰는 이유가 애초에 파일 본문을 서버가 만지지 않는 것**이었고,
`headObject`는 그 이유를 무너뜨리지 않는다. 본문이 없는 HTTP HEAD라 같은 리전에서
10~30ms다. 사진 10장(최대 100MB) 기준으로 비교하면 부담이 자릿수로 다르다.

| | 서버 프록시 | presigned + HeadObject |
| --- | --- | --- |
| 서버가 옮기는 바이트 | 100MB in + 100MB out | 0 |
| 톰캣 스레드 점유 | 40~160초 (모바일 업로드 5~20Mbps) | 순차 100~300ms |
| 힙·임시 디스크 | 동시 업로드 × 파일 크기 | 없음 |
| 업로드 중 재배포 | `systemctl restart` 시 진행 중인 업로드 전부 실패 | 무관 |
| 네트워크 끊김 | 서버까지 실패, 처음부터 | 앱이 S3에 직접 재시도 |

결정적인 것은 스레드다. 톰캣 기본 스레드 수는 200이고, 느린 모바일 업로드가 그 스레드를
수십 초씩 점유하면 **업로드와 무관한 로그인·조회 API까지 같이 대기한다.** 업로드가 서비스
전체를 인질로 잡는 구조가 된다. presigned에서는 그 대기가 S3에서 일어난다.

프록시가 맞는 경우는 서버가 어차피 내용을 봐야 할 때(해시·리사이즈·검열)나 파일이 작을 때다.
10MB 사진은 정확히 반대 조건이다.

또한 클라이언트 왕복도 늘지 않는다. `headObject`는 이미 존재하는 [3] 요청 **안에서**
일어나는 서버↔S3 사이드 콜이다.

### 검증하지 않고 앱을 신뢰한다

채택하지 않았다. 현상 유지이고 비용이 0이라는 점에서 진지한 후보였다. 실제로 `PUT` 실패는
드물고, 앱이 성공 응답을 확인한 뒤에만 [3]을 보내면 어긋날 일이 거의 없다.

문제는 **어긋났을 때 영구적이고 조용하다**는 것이다. 깨진 이미지는 저절로 낫지 않고,
서버는 그런 기록이 몇 건인지조차 모른다. 사용자가 신고해도 원인을 좁힐 단서가 없다.
사고 확률은 낮지만 손해가 영구적이고 관측 불가능한 쪽이라, 수십 ms와 맞바꿀 만하다.

### S3 이벤트 알림으로 업로드 완료를 수신한다

채택하지 않았다. S3 → SQS/Lambda → 서버로 `ObjectCreated`를 받으면 가장 정확하고,
서버가 요청 처리 중에 S3를 부르지 않아도 된다.

그러나 **비동기라서 타이밍 문제가 생긴다.** 앱이 `PUT` 직후 기록을 저장하면 이벤트가
아직 도착하지 않았을 수 있고, 그때 "업로드 안 됨"으로 거절하면 정상 흐름이 실패한다.
결국 대기·재시도·유예 로직이 붙는데, 이는 `headObject` 한 줄로 없앨 수 있는 복잡도다.
SQS 큐와 소비자라는 인프라도 새로 생긴다.

썸네일 생성처럼 업로드 이후의 비동기 작업이 실제로 필요해지면 그때 다시 검토한다.
그 시점에는 이벤트 파이프라인 자체가 값을 하므로 판단이 달라진다.

### `upload_session` 테이블로 PENDING → CONFIRMED를 추적한다

채택하지 않았다. presigned 발급 시 `PENDING` 행을 남기고 기록 저장 시 `CONFIRMED`로
바꾸면, 검증과 고아 객체 추적(#162)을 같은 테이블로 처리할 수 있다는 장점이 있다.

그러나 **행이 있다는 것이 객체가 있다는 뜻은 아니다.** 발급 시점에 쓰는 행이므로
업로드 성공을 증명하지 못하고, 결국 `headObject`가 여전히 필요하다. 즉 이 안은 A안의
대안이 아니라 A안 **위에 얹는 것**이며, 마이그레이션과 정리 배치를 추가로 요구한다.

고아 객체 정리는 #162에서 독립적으로 다루고, 그 설계에서 이 테이블이 필요하다고 판단되면
그때 도입한다. 이 ADR의 범위는 "붙이려는 객체가 있는가"까지다.

## 결과

### 장점

- 깨진 이미지가 기록에 저장되는 경로가 닫힌다.
- 실패가 요청 시점에 드러난다. 앱이 어느 장을 다시 올려야 하는지 즉시 알 수 있다.
- S3 장애와 사용자 입력 오류가 다른 코드로 분리되어, 앱이 "재업로드"와 "재시도"를 구분한다.
- presigned 구조가 그대로 유지된다. 파일 본문은 여전히 서버를 거치지 않는다.
- 인프라 추가가 없다. `S3Client` 빈 하나와 검증 지점 한 곳이다.
- upload 패키지가 S3를 계속 가려, 인수 테스트가 S3 없이 돈다.

### 비용과 주의점

- 기록 저장 응답이 사진 수에 비례해 느려진다. 10장이면 100~300ms. 계측해서 지켜봐야 한다.
- **기록 저장이 S3 가용성에 묶인다.** 지금까지 S3가 죽어도 기록 저장은 됐지만(이미지만 깨졌을 뿐)
  이제는 저장 자체가 실패한다. 의도한 트레이드오프지만, S3 장애 시 영향 범위가 넓어진 것은 사실이다.
- S3 HEAD 요청 요금이 발생한다. 1,000건당 약 $0.0004로, 사진 500만 장을 검증해도 $2 수준이라
  실질적인 제약은 아니다.
- **반대 방향의 정합성은 여전히 열려 있다.** 업로드는 됐지만 기록에 붙지 않은 고아 객체는
  이 결정으로 줄지 않는다(#162).
- `objectKey`의 소유자 검증은 이 ADR의 범위가 아니다. 지금은 `travel-records/{남의 memberId}/...`
  형태의 키를 보내도 서버가 막지 않으며, `headObject`는 존재만 볼 뿐 소유를 보지 않는다.
  키가 UUID라 추측은 어렵지만, `TravelRecordDetailResponse`가 `objectKeys`를 그대로 내려주므로
  키 자체는 클라이언트에 노출되어 있다. 별도 이슈로 다룬다.
