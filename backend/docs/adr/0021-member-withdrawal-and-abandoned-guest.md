# ADR 0021. 회원 탈퇴와 버려진 게스트는 행을 남기고 이벤트로 알린다

- 상태: 제안
- 날짜: 2026-10-22
- 관련: ADR 0009, ADR 0011(refresh 토큰), ADR 0015(게스트), ADR 0020(애플 로그인)

---

## 문제

회원이 탈퇴할 수 있어야 한다. 게스트도 탈퇴할 수 있어야 한다. 정해야 할 것은 네 가지다.

- 회원 행을 지울 것인가
- 같은 소셜 계정으로 다시 가입하면 어떻게 되는가
- 탈퇴한 회원의 토큰을 어떻게 막는가
- 회원의 다른 데이터(여행 기록·태그·피드백·사진)는 누가 지우는가

탈퇴와 비슷하게 아무도 쓰지 않게 되는 회원이 하나 더 있다. 게스트로 사용하던 사람이 이미 가입한 소셜 계정으로
로그인하면 기존 회원으로 들어가고(ADR 0015), 두고 떠난 게스트 회원에는 아무도 접근할 수 없다.
지금까지는 그 게스트의 refresh만 폐기하고 행·기록은 표시 없이 남았다.

`member`를 외래 키로 참조하는 테이블은 `travel_record`, `tag`, `refresh_token`, `service_feedback`이고,
모두 `ON DELETE` 설정이 없다.

## 결정

### 행은 남기고 개인정보만 지운다 (soft 탈퇴)

`DELETE /api/v1/members/me`는 `member.withdrawn_at`(V26)을 채우고 다음과 같이 바꾼다.

| 컬럼 | 탈퇴 후 | 이유 |
|---|---|---|
| `name` | `탈퇴한 회원` | 제공자가 준 이름. 구글은 실명일 수 있다 |
| `nickname` | `탈퇴한 회원` | 다른 회원에게 보이는 이름 |
| `provider_id` | `NULL` | 아래 재가입 참고 |
| `provider` | 그대로 | 어떤 로그인 방식이었는지 운영 통계에 남긴다 |
| `uuid`, `id` | 그대로 | 다른 테이블이 참조한다 |

이미 탈퇴했으면 아무것도 하지 않고 `204`를 준다(멱등).
회원 행을 실제로 지우는 것은 모든 컨텍스트가 자기 데이터를 정리한 뒤의 작업이다.

### 같은 소셜 계정으로 다시 가입하면 새 회원이다

`(provider, provider_id)`에 UNIQUE가 있으므로 `provider_id`를 비운다. MySQL은 NULL끼리 같은 값으로 보지 않으므로
여러 탈퇴 회원이 있어도 충돌하지 않는다. 같은 카카오 계정으로 다시 로그인하면 기존 회원을 찾지 못해
새 회원으로 가입하고(`isNewMember = true`), 탈퇴 전 기록은 이어지지 않는다. 재가입을 일정 기간 막지 않는다.

### 탈퇴를 이벤트로 알린다

`MemberService.withdraw`는 처음 탈퇴할 때만 `MemberWithdrawn(memberId, provider, withdrawnAt)`을 발행한다.
이벤트는 엔티티를 담지 않는다.

- **auth**: `MemberRefreshTokenRevoker`가 `@EventListener`(동기)로 받아 회원의 refresh를 모두 폐기한다.
  게스트 승격(`GuestPromoted`, ADR 0015 #460)도 같은 리스너가 받는다.
  같은 트랜잭션이라 폐기가 실패하면 탈퇴도 롤백된다. member가 `RefreshTokenService`를 직접 부르지 않으므로
  의존 방향은 auth → member로 유지된다.
- **다른 컨텍스트**(그룹·여행 기록·미디어): 아직 받지 않는다. 받을 때는 탈퇴가 커밋된 뒤에 처리하도록
  `@TransactionalEventListener(phase = AFTER_COMMIT)`를 쓴다.

회원 컨텍스트에서 처음 발행하는 이벤트이고, 같은 트랜잭션에서 실행되는 동기 `@EventListener`도 처음이다.
(태그·여행 기록은 이미 캐시 무효화 이벤트를 `@TransactionalEventListener`로 쓰고 있다.)

### 남은 access token(최대 30분)은 회원 API와 재발급에서만 막는다

access token은 무상태라 탈퇴하거나 버려져도 만료까지 유효하다. JWT 필터에서 요청마다 회원을 조회하지 않는다
(ADR 0009, 커넥션 풀 고갈 이력). 대신 다음 경로에서 막는다.

| 경로 | 동작 |
|---|---|
| `GET /members/me`, `PATCH /members/me/nickname` | 서비스 트랜잭션에서 회원을 조회해 활동 중이 아니면 `401 INACTIVE_MEMBER` |
| `POST /auth/token/refresh` | refresh는 탈퇴·버려질 때 모두 폐기된다. 폐기와 재발급이 동시에 와도 회원이 활동 중이 아니면 `401 INVALID_REFRESH_TOKEN` |
| 소셜 로그인 + 탈퇴했거나 버려진 게스트의 access token | 승격하지 않고 게스트 토큰이 없는 로그인으로 처리 |

> 2026-10-24 구현 업데이트(#448): 회원 API의 응답을 `404 MEMBER_NOT_FOUND`에서 `401 INACTIVE_MEMBER`로 바꿨다.
> "회원이 없다"가 아니라 "이 토큰으로는 더 쓸 수 없다"는 뜻이라, 앱이 다른 인증 오류처럼 로그아웃하게 한다.
> 관리자가 다른 회원을 찾는 경우는 `404`를 유지한다.

여행 기록 작성처럼 그 밖의 경로는 30분 동안 허용한다. 그 사이 만든 데이터도 `member_id`가 같으므로
각 컨텍스트가 `MemberWithdrawn`을 받아 지울 때 함께 지워진다. 막아야 할 경로가 생기면
그 서비스 트랜잭션에서 `isActive()`를 확인한다.

> 2026-10-28 구현 업데이트: 남은 토큰으로 데이터나 비용을 만드는 세 경로를 막는다. 여행 기록 작성,
> 업로드 URL 발급(S3), 공유 영상 생성(렌더러)이 서비스에서 `ActiveMemberGuard`를 불러 활동 중이 아니면
> `401 INACTIVE_MEMBER`다. 그룹의 `SocialMemberGuard`도 이 가드를 쓴다. 기록 작성은 이미 여는 트랜잭션 안에서,
> 업로드 URL 발급은 트랜잭션이 없어 커넥션을 한 번 빌려 확인한다.
>
> 나머지 경로(기록 수정, 태그, 장소 검색, 서비스 의견)는 여전히 30분 동안 열려 있다. 그래서 위 근거가 성립하려면
> **파기는 `withdrawn_at`(버려진 게스트는 `abandoned_at`)에서 access token 유효시간(30분)이 지난 뒤에 시작해야 한다.**
> 탈퇴 이벤트를 받자마자 지우면 그 뒤 30분 동안 만든 데이터가 파기 대상에서 빠진다(#435).

### 두고 떠난 게스트는 버려진 게스트로 표시하고 이벤트로 알린다

이미 가입한 소셜 계정으로 로그인하면서 게스트를 두고 떠나면(`EXISTING_ACCOUNT`), `MemberJoinService`가 같은 트랜잭션에서

1. 게스트의 `abandoned_at`(V27)을 채우고 (`Member.abandon`, 게스트만, 멱등)
2. `GuestAbandoned(guestMemberId, abandonedAt)`를 발행한다.

- 행과 기록은 지우지 않는다. 게스트의 이름·`provider_id`는 서버가 만든 값이라 개인정보가 아니므로 비우지 않는다.
- 게스트의 refresh 폐기는 탈퇴와 같이 `MemberRefreshTokenRevoker`가 이 이벤트를 동기로 받아 로그인과 같은 트랜잭션에서 한다.
  (처음에는 `AuthService`가 로그인 처리에서 직접 폐기했으나, 탈퇴와 방식을 맞추고 auth가 member의 결과를 해석하지 않도록 옮겼다.)
- 여행 기록·미디어는 나중에 `AFTER_COMMIT` 리스너로 받아 파기 기간을 정해 지운다.
- 로그인 응답에 `guestAbandoned`(기존 필드는 그대로)를 추가한다. 로그인 전에는 기존 계정이 있는지 알 수 없으므로,
  앱은 로그인 **뒤에** "게스트로 남긴 기록은 이어지지 않았다"고 안내한다.

### 활동 중인 게스트만 승격한다

`isActive()`는 탈퇴하지도, 버려지지도 않은 회원이다. 탈퇴해도, 버려져도 `provider`는 `GUEST`로 남는다.
승격이 `provider == GUEST`만 보면, 그 게스트의 남은 access token으로 소셜 로그인했을 때 승격되어 회원이 되살아난다.
`MemberJoinService.findGuest`는 활동 중인 게스트만 돌려주고(그 밖이면 게스트 토큰이 없는 로그인으로 처리),
`Member.promote`도 활동 중인 게스트가 아니면 예외를 던진다.
같은 이유로 버려진 게스트의 토큰으로 다시 기존 계정에 로그인해도 `GuestAbandoned`를 다시 발행하지 않는다.

## 검토한 대안

### 즉시 행 삭제 (hard delete)

채택하지 않았다. 외래 키 때문에 회원의 모든 데이터를 먼저 지워야 하는데, 그 데이터는 다른 컨텍스트가 가지고 있다.
회원 컨텍스트가 모두 지우면 컨텍스트 경계를 넘고, `ON DELETE CASCADE`를 걸면 S3 원본처럼 DB 밖의 데이터를 놓친다.

### JWT 필터에서 매 요청 탈퇴 여부 확인

채택하지 않았다. ADR 0009에서 요청마다 회원을 조회하다 커넥션 풀이 고갈된 이력이 있다.
탈퇴 회원 ID를 캐시하는 방법도 있지만, 30분 창을 위해 상태를 하나 더 둘 만큼의 위험은 아니라고 봤다.

### 버려진 게스트의 기록을 기존 회원에게 합치기

채택하지 않았다. ADR 0015에서 기존 계정을 우선하고 게스트 기록은 잇지 않기로 했다.
합치려면 두 회원의 태그 이름 중복 등 컨텍스트마다 규칙이 필요하다. 표시와 이벤트가 있으면 나중에 합치는 작업도 이 이벤트로 시작할 수 있다.

### 재가입을 일정 기간 막기

채택하지 않았다. 막으려면 탈퇴한 회원의 `provider_id`(또는 해시)를 남겨야 해서 개인정보를 지운다는 목적과 맞지 않는다.

## 결과

### 장점

- 다른 컨텍스트가 준비되지 않아도 탈퇴를 제공할 수 있다. 각 컨텍스트는 이벤트를 받는 리스너만 추가하면 된다.
- 개인정보(이름·닉네임·`provider_id`)는 탈퇴 즉시 지워진다.

### 비용과 주의점

- 리스너가 생기기 전까지 탈퇴한 회원과 버려진 게스트의 여행 기록·태그·피드백·S3 원본은 DB와 저장소에 남는다(이슈 #435).
  파기 기간과 순서(기여 사진 → 그룹 → 기록 → 원본)는 각 컨텍스트 작업에서 정한다.
- 관리자 화면의 회원 수 집계에는 탈퇴 회원이 포함된다.
- `withdrawn_at`은 기존 `Clock` 빈(Asia/Seoul)으로 정하고, refresh의 `revoked_at`은 `LocalDateTime.now()`(서버 기본 시간대)로
  정한다. 서버 시간대가 UTC면 두 값이 9시간 차이 난다.
  > 2026-10-28 구현 업데이트: 더는 차이 나지 않는다. `Clock` 빈이 UTC가 됐다(#501). `revoked_at`은 원래 UTC였다.
  > 앱의 `main()`이 JVM 기본 시간대를 UTC로 고정하기 때문이다. #521부터는 `revoked_at`도 같은 `Clock`으로 정한다.

### 남은 일

- **애플 토큰 철회**: 심사 지침 5.1.1(v)에 따라 애플 회원이 탈퇴하면 애플 토큰을 철회(`/auth/revoke`)해야 한다(ADR 0020).
  철회에는 앱이 보내는 authorization code와 Team ID·Key ID·`.p8` 키가 필요해 이번 결정에는 넣지 않았다.
  `MemberWithdrawn`(provider = APPLE)을 받는 리스너로 추가할 수 있다.
- **카카오 연결 끊기**: 카카오 회원이 탈퇴하면 카카오 연결 끊기(unlink)를 호출하는 것이 권장된다. 같은 방식으로 추가할 수 있다.
- **파기 기간**: 탈퇴 회원과 버려진 게스트의 데이터를 언제 지울지 정하고 각 컨텍스트에 리스너·배치를 만든다(이슈 #435).
  파기 기간은 access token 유효시간(30분)보다 길어야 한다(위 2026-10-28 구현 업데이트).
