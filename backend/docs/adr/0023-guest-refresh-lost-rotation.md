# ADR 0023. 게스트의 refresh 회전 응답 유실은 후속 토큰이 쓰이지 않았을 때만 재발급한다

- 상태: 제안
- 날짜: 2026-10-23
- 관련: #439, #440, ADR 0011, ADR 0015

---

## 문제

ADR 0011은 이미 폐기된 refresh가 다시 오면 탈취로 보고 회원의 유효한 refresh를 모두 폐기한다.
그런데 정상 사용자도 이 상황을 만든다.

1. 클라이언트가 refresh A로 재발급을 요청한다.
2. 서버가 A를 폐기하고 B를 발급해 커밋한다.
3. 응답이 도착하기 전에 앱이 종료되거나 네트워크가 끊겨, 클라이언트는 여전히 A를 가진다.
4. 다음에 앱을 열면(몇 초 뒤일 수도, 며칠 뒤일 수도 있다) A로 요청하고, 서버는 B까지 폐기한다.

소셜 회원은 다시 로그인하면 된다. 게스트는 다시 로그인할 수단이 없어 **계정과 기록을 영구히 잃는다.**

## 결정

### 소셜 회원은 ADR 0011을 그대로 따른다

재사용이 감지되면 모두 폐기하고 401로 응답한다. 클라이언트는 로그인 화면으로 보낸다.
카카오도 회전 응답을 놓치면 다시 로그인하게 한다. 탈취가 의심되는 상황이므로 이쪽이 안전하다.

### 게스트는 후속 토큰이 아직 쓰이지 않았으면 재발급한다

회전할 때 이전 토큰에 후속 토큰의 id(`replaced_by_id`)를 남긴다.
폐기된 게스트 토큰이 다시 오면 후속 토큰을 본다.

| 상황 | A가 다시 올 때 B | 처리 |
| --- | --- | --- |
| 응답 유실 | 유효(아무도 안 씀) | B를 폐기하고 C를 발급, A와 B 모두 C를 가리킨다 |
| 정상 사용자가 B로 넘어간 뒤 탈취자가 A 사용 | 회전으로 폐기됨 | 탈취로 보고 모두 폐기 |
| 탈취자가 먼저 A→B, 그 뒤 정상 사용자가 A 사용 | (탈취자가 아직 안 썼다면) 유효 | 정상 사용자에게 C, B 폐기 → 탈취자가 끊긴다 |
| 직전보다 오래된 토큰 | 후속이 이미 폐기됨 | 탈취로 보고 모두 폐기 |

후속 토큰은 쓰이면 반드시 회전으로 폐기되므로, "후속 토큰이 아직 유효하다"가 곧 "아무도 쓰지 않았다"이다.
그래서 폐기 사유를 따로 저장하지 않는다. 로그아웃이나 전체 폐기로 후속이 폐기된 경우도 재발급하지 않는다.

재발급 때 A도 새 후속 C를 가리키게 해, 응답 유실이 연달아 일어나도 A로 다시 이어진다.

### 폐기와 발급을 한 트랜잭션에서 한다

체인을 남기려면 새 토큰의 id가 필요하다. 그래서 기존의 "검증·폐기 트랜잭션 → 발급 트랜잭션" 두 단계를
`RefreshTokenService#rotate` 한 트랜잭션으로 합쳤다. 재사용일 때 예외 대신 `Optional.empty`로 신호하고
401은 트랜잭션 밖에서 던지는 방식(ADR 0011)은 그대로다.

재발급 경로는 A(토큰 해시로) → B(id로) 순서로 행을 잠근다. 정상 회전은 한 행만 잠그므로 잠금 순서가 엇갈리지 않는다.

## 검토한 대안

### 짧은 유예 시간(grace period)

Okta·Auth0처럼 회전 직후 몇 초~몇 분 동안 이전 토큰을 허용한다. 재시도는 막지만,
앱을 꺼 둔 채 몇 시간 뒤 다시 여는 경우를 막지 못한다. 유예를 몇 시간으로 늘리면 그동안 탈취된 토큰도 구분하지 못한다.

### 회전하지 않기 (Google, Apple)

응답 유실 문제가 사라지지만, 탈취된 토큰을 감지할 수단도 사라진다.
기기 키 바인딩(DPoP, RFC 9449) 없이 회전을 끄는 것은 이르다고 봤다.

### 게스트 없애기

근본 해결이지만, 가입 전 체험 흐름과 소셜 로그인 이탈률 때문에 아직 없앨 수 없다.
게스트에게 소셜 계정 연결을 권하고 승격률을 보는 작업은 #440에서 한다.

## 결과

### 장점

- 게스트가 회전 응답을 놓쳐도 경과 시간과 무관하게 계정을 잃지 않는다.
- 소셜 회원의 탈취 감지는 전혀 약해지지 않는다.
- 게스트를 없애면 `reissueLostRotation` 분기만 지우면 된다.

### 비용과 주의점

- 정상 사용자와 탈취자가 둘 다 A만 가진 채 어느 쪽도 다음으로 넘어가지 않으면, 서로 번갈아 재발급받는 동안 감지되지 않는다.
  한쪽이 한 번이라도 넘어가면 감지된다. 토큰을 키체인에 두는 앱에서 탈취 가능성은 낮고, 게스트에게 응답 유실은 곧 계정 소실이라 감수한다.
- `replaced_by_id`는 같은 테이블을 가리키지만 FK를 두지 않는다. 일괄 삭제 때 행 순서에 따라 제약 위반이 날 수 있고,
  후속이 지워졌다면 재발급하지 않으면 되기 때문이다.
