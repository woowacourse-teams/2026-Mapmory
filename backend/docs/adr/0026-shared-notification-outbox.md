# ADR 0026. 알림 발송을 공통 Outbox로 기록하고 기기별로 처리한다

- 상태: 제안
- 날짜: 2026-10-29
- 관련: #545, #553, ADR 0022, ADR 0025

## 문제

영상 생성은 서버에서 비동기로 끝나므로 앱이 종료된 상태에서도 완료를 기기에 알려야 한다.
영상 완료를 DB에 저장한 뒤 FCM을 호출하는 사이 서버가 종료되면 영상은 완료됐지만 알림은 발송되지 않는다.
반대로 DB 커밋 전에 외부에 발송하면 트랜잭션이 롤백돼도 완료 알림이 전달될 수 있다.

영상뿐 아니라 그룹의 앨범 알림도 알림 발송 기능을 사용한다. 영상 전용 테이블을 만들면 발송 상태,
재시도, 기기별 실패 처리와 운영 관측을 다른 기능에서 다시 만들어야 한다.

현재 그룹 알림은 ADR 0022의 커밋 후 비동기 이벤트를 사용한다. 그 흐름에 Outbox는 아직 연결되어 있지 않다.
이 ADR은 공통 구조를 제안하며, 그룹 쪽 적용 여부·일정·세부 정책을 결정하거나 변경하지 않는다.

## 결정

### 공통 `notification_outbox`에 기기별 발송 기록을 둔다

- 영상 전용 `video_job_id` 대신 이벤트 유형 `event_type`, 사건 식별자 `event_key`, 유형별 `payload`를 사용한다.
- 한 행은 **하나의 사건을 하나의 푸시 등록 기기에 발송할 작업**이다. 같은 사건의 여러 기기는 각각 별도 행을 둔다.
- `member_id`, `push_token_id`는 요청 당시의 수신 대상 식별자다. FCM 토큰 원문·인증 정보·서명된 다운로드 URL은 Outbox에 저장하지 않는다.
- 영상 요청에 수신 등록 ID가 없으면 영상만 생성하고 알림 이벤트는 만들지 않는다.
- `push_token_id`에는 등록 삭제를 막거나 이벤트를 연쇄 삭제하는 FK를 두지 않는다. 발송 직전에 등록의 존재·회원 소유권·회원 상태를 확인하고 대상이 없으면 발송을 생략한다.
- `payload`는 유형별로 필요한 최소 데이터만 담는다. 영상 완료의 초안은 `{"jobId": 15}`다. payload 스키마·버전 관리와 보관 기간은 구현 시 정하고 위치 기록·비밀 값 등 불필요한 데이터를 넣지 않는다.

### 이벤트 키와 중복 범위를 명시한다

- `event_key`는 같은 사건의 재시도에서 동일한 값을 쓰고, 다른 사건에는 다른 값을 쓴다. 유형·생산자별 네임스페이스를 정해 충돌을 피한다.
- 영상 완료 키의 초안은 `video:15:completed`처럼 영상 작업 ID와 완료 유형을 조합한다. 첫 생성과 재시도가 같은 작업이면 키도 같다.
- UNIQUE `(event_key, push_token_id)`로 같은 사건을 같은 기기에 중복 저장하지 않는다. 같은 사건의 다른 기기에는 각각 한 행을 기록할 수 있다.
- 키의 대소문자 구분은 `utf8mb4_bin`으로 명시한다. 유일성은 DB에 행이 남아 있는 동안에만 보장하므로, 발송 기록 삭제 후 재생성 방지와 보존 기간은 함께 정한다.
- 같은 앨범에 서로 다른 사진 추가가 발생하는 경우를 예로 들면, 앨범 ID만으로는 두 사건을 구분할 수 없다. **그룹의 사건 키와 수신 기기 확정 시점은 그룹 담당 팀과 협의할 후속 사항**이다.
- DB 중복 방지와 FCM에 정확히 한 번 표시하는 보장은 다르다. FCM 접수 직후 발송 결과 저장 전에 워커가 종료되면 같은 알림이 다시 발송될 수 있다.

### 영상 완료와 이벤트를 하나의 DB 트랜잭션에 저장한다

```text
렌더링 → S3 업로드 성공
          ↓
한 DB 트랜잭션: 영상 COMPLETED + Outbox PENDING 저장
          ↓ 커밋 후
별도 발송 워커: 이벤트 선점 → FCM 요청 → 결과 기록
```

- 완료 상태와 Outbox 저장 중 하나가 실패하면 둘 다 롤백한다. 같은 트랜잭션에서 저장하는 것이 필수이며 각각 `REQUIRES_NEW`로 분리하지 않는다.
- FCM 호출은 커밋 후에 하고, 호출을 기다리는 동안 DB 트랜잭션이나 행 잠금을 유지하지 않는다.
- 영상 완료·이벤트 저장이 롤백돼도 이미 성공한 S3 업로드까지 DB가 되돌릴 수는 없다. 현재 영상 워커는 완료 기록의 일시적 DB 오류를 최대 세 번 즉시 재시도하고, 기록 실패만으로 `FAILED`를 저장하지 않는다. 자동 복구와 미사용 객체 정리는 아직 구현하지 않았다.
- 그룹이 나중에 Outbox를 사용하려면 그룹 변경과 이벤트 저장이 같은 DB 트랜잭션에 참여해야 한다. 단순히 기존 `AFTER_COMMIT` 리스너에서 Outbox를 추가 저장하면 둘 사이의 유실 가능성을 없애지 못한다.

### 발송 워커는 상태·기한·실행 식별자를 관리한다

| 상태 | 의미 |
| --- | --- |
| `PENDING` | 발송 또는 재시도를 기다림 |
| `PROCESSING` | 워커가 선점해 처리 중 |
| `SENT` | FCM이 발송 요청을 접수함. 기기 표시·사용자 확인은 별도 |
| `FAILED` | 영구 오류 또는 재시도 한도 초과 |
| `SKIPPED` | 수신 등록 삭제 등으로 발송하지 않음 |

- 여러 워커는 짧은 트랜잭션에서 발송 가능한 행을 잠금·선점한 뒤 커밋하고 외부 발송을 수행한다.
- `claim_token`과 `lease_expires_at`으로 선점 실행과 만료 시각을 구분한다. 종료된 워커의 만료된 작업은 재선점할 수 있어야 한다.
- 결과 저장 시 상태와 `claim_token`을 함께 조건으로 확인해 이전 워커가 새 선점의 DB 결과를 덮어쓰지 못하게 한다. 이 조건만으로 만료된 이전 워커가 외부 FCM에 중복 요청하는 것까지 막을 수는 없다.
- 일시 오류는 `attempt_count`와 `next_attempt_at`으로 제한된 재시도를 하고, 무효 대상은 재시도 정책에 따라 정리하거나 생략한다. 정확한 간격·횟수·오류별 처리는 구현 전에 결정한다.
- `next_attempt_at`은 첫 이벤트 생성 시 서버의 UTC 현재 시각으로 설정한다. 서비스 시계와 DB 세션 시간대가 UTC 기준과 일치하는지 검증한다.

## 검토한 대안

### 영상 전용과 그룹 전용 테이블

각 기능이 독립적으로 스키마·처리 속도를 조정하기 쉽지만, 동일한 기기 발송·상태·재시도 코드를 두 번 관리하게 된다.
공통 알림 전달 요구가 있으므로 우선 공통 구조를 제안한다. 발송량·보관 정책·격리 요구가 실제로 달라지면 재검토한다.

### 영상 전용 `video_job_id`를 공통 테이블에 둔다

그룹 등 영상 이외 이벤트에는 의미가 없고, 이벤트별 컬럼이 늘어난다. 사건 식별과 payload를 공통 필드로 분리한다.

### 별도의 메시지 브로커를 먼저 도입한다

작업을 독립 확장하기 좋지만 현재는 DB Outbox와 워커만으로 시작할 수 있다. 브로커 도입 여부는 처리량·운영 요구를 확인한 뒤 결정한다.

### FCM 직접 발송 또는 커밋 후 메모리 이벤트만 사용한다

DB 커밋과 외부 발송 사이에 서버가 중단되면 발송할 일을 잃을 수 있으므로 영상 완료 알림의 내구성 요구를 충족하지 못한다.

## 결과와 주의점

- 영상 담당 범위는 공통 발송 구조의 초안과 영상 완료 이벤트 연결이다. 그룹 API·이벤트·리스너를 이 작업에서 수정하지 않는다.
- 상태, 발송 실패·오류 분류, 기기별 이력과 재시도 정책이 한곳에 모이는 대신 공통 워커의 오류나 특정 유형의 대량 유입이 다른 유형에도 영향을 줄 수 있다. 격리·공정성·운영 기준은 실제 요구를 확인해 정한다.
- `PENDING`·만료된 `PROCESSING`의 조회 인덱스가 필요하며, 실제 실행 계획과 데이터 규모를 보고 검증한다.
- 발송 요청 성공 후 로그아웃하거나 재등록한 경우 이미 FCM에 접수된 메시지는 회수할 수 없다. 현행 기기 식별·로그아웃 한계는 #553에서 다룬다.
- 알림 발송 실패와 영상 생성 상태는 별개다. 발송 오류만으로 `COMPLETED` 영상을 `FAILED`로 바꾸지 않는다.

## 구현 상태와 남은 결정

- 로컬 V39, 엔티티, 영상 완료와 Outbox 저장, 선점·만료 복구·결과 기록 메서드와 영상 알림 FCM 발송 워커가 구현되었다. 실제 FCM 발송과 기기 수신, 배포·운영 DB 적용 여부는 확인하지 않았다. 최신 상태는 [알림 팀 가이드](../notification-team-guide.md)를 따른다.
- V39가 이미 적용된 환경이 있다면 기존 파일을 수정하지 말고 새 마이그레이션으로 변경한다.
- 이벤트 생성의 중복 처리 시 트랜잭션 롤백 없이 안전하게 기존 결과를 반환하는 방식, 보존 기간, 최대 시도 횟수와 재시도 간격을 정하고 테스트한다.
- 영상 완료 저장의 커밋·롤백, 중복 완료 호출, 선점 잠금·만료 복구, 만료 토큰의 결과 저장 거부는 MySQL 통합 테스트로 확인했다. 실제 발송 흐름에서 동시 중복 이벤트, 늦은 결과, 무효 등록·토큰 갱신, 발송 직후 서버 종료는 추가 검증한다.
- 그룹 사용 여부, 발생 사건 ID, 수신 대상 확정 시점과 보관·재시도 정책은 그룹 담당 팀이 검토한다.
