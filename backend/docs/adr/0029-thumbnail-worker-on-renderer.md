# ADR 0029. 사진 썸네일은 렌더러 서버의 워커가 만든다

- 상태: 제안
- 날짜: 2026-11-08
- 관련: #631, #624, #186, ADR 0017, ADR 0018, ADR 0026

## 문제

썸네일이 하나도 없다. 운영 `record_media` 2,482행 중 `thumb_key`가 있는 행은 0개였다(2026-11-07). 저장 경로가 항상 `thumb_key = null`로 저장하고, 이미지를 줄이는 코드가 어디에도 없었다. 그래서 기록 목록, 앨범 카드, 앨범 그리드가 모두 수 MB짜리 원본을 받는다.

iPhone HEIC는 방향 정보가 HEIF `irot`와 EXIF 방향 두 군데에 있다. 앱이 원본을 그릴 때 둘을 겹쳐 적용하면 사진이 90도 꺾인다.

## 결정

### 렌더러 서버에서 같은 JAR의 워커로 만든다

공유 영상 워커가 도는 렌더러 서버에 썸네일 워커를 붙인다(`media.thumbnail.worker.enabled=true`). API 서버에서는 끈다.

- 변환은 Python 스크립트(`thumbnail/`, Pillow와 pillow-heif)가 맡는다. Java에는 HEIC 디코더가 없다.
- 워커는 썸네일이 없는 사진을 10초마다 20장씩 읽어 원본을 내려받고, 스크립트를 실행하고, 결과를 올린 뒤 `thumb_key`를 채운다.
- 같은 서버에서 공유 영상을 만들기 시작하면 하던 사진 한 장을 마친 뒤 쉰다(`RenderActivity`). 2GB 메모리를 나눠 쓰고, 썸네일은 늦어져도 원본이 보인다. 영상 워커는 그 한 장을 기다리지 않아, 최악에는 내려받기(최대 60초)·변환(30초)·올리기(60초) 동안 겹친다. 겹칠 때의 실제 메모리는 dev 렌더러에서 잰다.
- 한 쪽을 다 읽었는데 할 일이 없었으면(옛 키, 포기한 사진) 기다리지 않고 다음 쪽을 읽는다. 건너뛸 사진이 많아도 새 사진이 그만큼 늦어지지 않는다.
- 처음 돌 때 스크립트를 `--check`로 실행해 Python과 패키지를 확인한다. 준비되지 않았으면 썸네일만 멈추고 한 번 알린다. 공유 영상은 그대로 돈다.

### 키 규칙: 원본과 다른 경로에 둔다

```
원본:   {p}/travel-records/{memberId}/{name}.{ext}
썸네일: {p}/derived/thumb/{memberId}/{name}.webp
```

- 워커가 쓰고 지우는 곳을 `derived/` 아래로 묶어 원본을 덮어쓸 수 없게 한다(`S3ThumbnailStorage`가 막는다).
- 고아 객체 대조 배치(#186)는 `travel-records/`만 읽으므로 썸네일과 겹치지 않는다.
- 접두사를 붙이기 전에 저장된 옛 키처럼 이 형식이 아닌 원본은 썸네일을 만들지 않는다. `DerivedObjectKeys#thumbnailOf`가 빈 값을 돌려주고, 워커는 건너뛰며 한 번만 센다.

### thumb_key에는 S3에 올라간 것을 확인한 키만 넣는다

워커는 `PutObject`가 성공한 뒤에만 `UPDATE ... WHERE id = ? AND thumb_key가 비어 있음`으로 채운다. 그 전에는 비어 있어 앱은 원본을 본다. 썸네일 URL로 404를 받는 일이 없다.

`RecordMedia`는 `TravelRecord` 애그리거트 안의 엔티티다(ADR 0017). 그래도 `thumb_key`는 원본에서 정해지는 파생 데이터라 애그리거트의 불변식과 무관하다. 그래서 루트를 거치지 않고 `TravelRecordRepository`의 벌크 쿼리로 바로 읽고 채운다.

### 작업 테이블과 리스 없이 상태로 처리한다

공유 영상은 `share_video_job` 테이블과 리스를 쓴다. 썸네일은 쓰지 않는다. 할 일 목록이 "`thumb_key`가 비어 있음"이라는 상태 자체이고, 결과가 원본 키에서 정해지기 때문이다.

| 상황 | 처리 |
| --- | --- |
| 올린 직후 죽었다 | 다음 차례에 썸네일이 S3에 있으면 만들지 않고 채우기만 한다 |
| 늦게 깨어난 워커가 쓴다 | 같은 키에 같은 값이고, 비어 있을 때만 채워 덮어쓰지 않는다 |
| 기록 수정이 사진을 읽은 뒤 워커가 채우고, 그 수정이 사진 순서를 바꾼다 | 수정의 UPDATE가 모든 컬럼을 써서 `thumb_key`가 다시 비워진다. 다음 차례에 워커가 S3에서 썸네일을 찾아 다시 채운다 |
| 재시작 | 메모리의 커서만 잃고 처음부터 다시 돈다 |
| 배포 | 기존 사진도 같은 방식으로 채운다. 백필 전용 코드가 없다 |

렌더러를 두 대 이상으로 늘리면 행을 나눠 가져가야 한다(`id % 서버 수` 또는 리스). 그때 다시 검토한다.

### 삭제와의 경합: 만들어질 썸네일 키까지 정리 큐에 넣는다

워커가 썸네일을 올리고 `thumb_key`를 채우는 일과 사진을 지우는 일(사진 빼기, 기록 삭제, 회원 파기)이 겹칠 수 있다.

| 순서 | 막는 방법 |
| --- | --- |
| 행이 먼저 사라지고 워커가 채운다(0행) | 워커가 그 썸네일 키를 정리 큐(`orphaned_media`)에 넣는다 |
| 워커가 먼저 채우고, 삭제 쪽은 그 전에 키를 읽었다 | 삭제 쪽이 원본에서 만들어질 썸네일 키(`DerivedObjectKeys#thumbnailOf`)도 정리 큐에 넣는다. 회원 파기는 S3를 지우는 동안 이 틈이 수 초라, 행을 지운 같은 트랜잭션에서 넣는다 |

정리 배치는 지우기 직전에 다시 본다. 썸네일 키는 `thumb_key`로 쓰이거나 **그 원본이 아직 기록에 붙어 있으면** 쓰이는 중으로 보고 남긴다. 사진을 뺐다가 다시 붙인 경우, 워커가 "썸네일 있음"을 확인한 직후 배치가 지우면 `thumb_key`가 없는 객체를 가리키게 되기 때문이다. 원본 후보는 서버가 발급하는 확장자(jpg, png, webp, heic)로 만든다(`DerivedObjectKeys#originalCandidatesOf`).

없는 객체를 지우는 것은 S3에서 성공하므로, 썸네일이 만들어지지 않았어도 넣어 둔다. 버킷에 버전 관리가 켜져 있어 정리 배치는 모든 버전을 지우는 기존 `ObjectDeleter`를 쓴다. 지우다 실패하면 큐에 남아 다음에 다시 지운다.

설계 단계의 `RecordMedia#storedKeys()` 변경안(S2)은 쓰지 않았다. 키 규칙에 접두사가 필요해 도메인 엔티티 대신 서비스가 `DerivedObjectKeys`로 넣는다. 접두사 밖의 옛 키는 빈 값이라 건너뛴다.

### 실패

렌더러 배포(`install.sh`)는 Python 가상환경을 만들지 못해도 실패하지 않고 경고만 남긴다. 썸네일 워커는 기본으로 꺼져 있고, 켜도 위의 확인에서 멈출 뿐이라 공유 영상 렌더러가 배포 실패로 내려가는 일이 없다.

| 실패 | 처리 |
| --- | --- |
| 원본 내용 때문에 못 만든다(스크립트 종료 코드 2) | 다시 하지 않는다. 원본이 보인다 |
| 그 밖(종료 코드 1, 시그널 종료, 시간 초과, S3·DB 오류) | 다시 한다. 같은 사진이 3번 실패하면 건너뛴다 |

실패 기록은 메모리에 두고 6시간마다 비운다. 잠깐의 S3·DB 장애로 포기한 사진도 재시작을 기다리지 않고 다시 해 본다. 변환 환경 확인(`--check`)이 실패하면 10분 뒤 다시 확인한다.

메트릭:
- `mapmory.thumbnail.worker{result}`: `created`, `attached_existing`, `undecodable`, `failed`, `given_up`, `unsupported_key`, `orphaned`, `not_ready`
- `mapmory.thumbnail.backlog`: 한 시간이 넘었는데 썸네일이 없는 사진 수. 한 바퀴를 돌 때마다 갱신한다.

### 크기와 형식

- 긴 변 1080px WebP quality 75, 원본보다 키우지 않는다. 앱은 지금 원본을 받아 기기에서 1280px로 줄여 목록에 쓴다. 그보다 많이 작으면 흐려진다.
- 방향은 픽셀에 굽고 EXIF는 쓰지 않는다. 앱의 회전 코드가 아무 일도 하지 않게 되고, 위치 정보도 빠진다.
- 객체는 `Content-Type: image/webp`, `Cache-Control: max-age=31536000, immutable`로 올린다. 키에 UUID가 있어 내용이 바뀌지 않는다. `private`을 붙이면 CloudFront가 캐시하지 않는다. 접근은 서명 URL이 막는다.
- 펼칠 화소 수가 7,000만을 넘으면 만들지 않는다(종료 코드 2). 작은 PNG도 펼치면 GB 단위가 될 수 있다.

### 썸네일 키에는 판을 넣지 않는다

키가 원본에서 정해지고, 워커는 이미 있는 썸네일을 다시 만들지 않으며, 객체는 1년 동안 캐시된다. 그래서 변환 규칙을 바꿔야 할 때(크기, 형식, 방향 처리) 같은 경로에 다시 만들 수 없다. 그때는 `derived/thumb-v2/`처럼 새 경로를 정하고 `thumb_key`를 비워 다시 채운다.

## 고려한 대안

| 대안 | 판단 |
| --- | --- |
| S3 이벤트 + Lambda | 기존 사진은 따로 채워야 한다. 공용 계정에서 버킷 이벤트와 호출 권한을 받아야 한다. 수료 뒤 옮길 후보로 둔다. 스크립트는 그대로 쓸 수 있다 |
| 썸네일 전용 EC2 | 격리는 가장 좋지만 서버, 배포, 보안 그룹이 하나씩 는다. 렌더러 메모리가 모자라다고 측정되면 같은 JAR을 띄운다 |
| API 서버 안에서 변환 | Java에 HEIC 디코더가 없고, API와 CPU·메모리를 나눠 쓴다 |
| 앱이 만들어 올린다 | 기존 사진을 채울 수 없고, 업로드 한도(#619, 파일 수 기준)를 두 배로 쓴다 |

## 결과

- 목록이 원본 대신 수백 KB 이하의 썸네일을 받는다. 앱 수정은 필요 없다(응답 필드는 그대로이고 값만 바뀐다).
- API 서버는 목록 페이지를 메모리에 30분 둔다. 렌더러가 `thumb_key`를 채워도 다른 JVM이라 그 캐시를 지울 수 없어, 새 사진은 최대 30분 동안 원본으로 보인다. 그동안에도 원본이 보여 지금보다 나빠지지 않는다.
- 앨범 그리드는 응답에 썸네일 필드가 없어 이것만으로는 바뀌지 않는다. #624의 `thumbnailUrl`과 앱 수정이 따로 필요하다.
- 상세 화면은 원본을 그대로 써서 회전 문제가 남는다. 상세용 사본(`derived/display/`)은 후속 이슈에서 다룬다. 그때도 백필은 같은 방식으로 자동으로 돈다.
- 렌더러가 멈추면 썸네일도 멈추지만 목록은 원본으로 계속 보인다.
