# ADR 0030. 요청 모양을 바꾸는 쓰기 API는 v2로 나눈다

- 상태: 제안
- 날짜: 2026-11-11
- 관련: #690, #691

## 문제

기록 사진첩이 사진을 촬영일로 묶는데, 촬영일이 사진을 고른 기기에만 있었다. 앱 데이터가 지워지거나, 다른 기기로 로그인하거나, 그룹 멤버가 보면 사진이 "날짜 미상"으로 묶였다. 촬영일을 서버에 저장하려면 생성·수정 요청이 사진마다 촬영일을 실어야 한다.

v1 요청은 사진을 `objectKeys: ["key1", "key2"]` 문자열 목록으로 받는다. 이걸 객체 목록으로 바꾸면 스토어에 깔린 예전 앱의 요청이 깨진다. 옆에 `capturedDates` 맵을 붙이면 호환은 되지만, 한 사진의 정보가 두 필드로 나뉘어 서로 어긋날 수 있다. 앞으로 좌표처럼 사진 정보가 늘 때마다 맵도 늘어난다.

## 결정

### 생성·수정만 v2를 만든다

```
POST /api/v2/travel-records
PUT  /api/v2/travel-records/{id}

"photos": [
  { "objectKey": "...", "capturedDate": "2026-08-11" },
  { "objectKey": "...", "capturedDate": null }
]
```

- `photos` 배열 순서가 사진 순서다. 나머지 필드와 응답은 v1과 같다.
- v1 쓰기는 그대로 `objectKeys`만 받는다. 촬영일을 보내지 않는 수정은 저장된 촬영일을 지우지 않는다.
- 두 버전 모두 `TravelRecordCommand`로 바꿔 같은 서비스를 탄다. 버전은 웹 계층에만 있다.

### 조회는 v1 그대로 둔다

응답에 필드가 늘어나는 변경(`media[].capturedDate`, 앨범 `photos[].capturedDate`)은 예전 앱이 모르는 필드로 무시한다. 같은 응답을 두 벌 두지 않는다.

### 언제 v2를 만드는가

- **만든다:** 기존 필드의 타입이나 모양을 바꿔야 해서 예전 앱의 요청이나 해석이 깨질 때.
- **만들지 않는다:** 선택 필드 추가, 응답 필드 추가처럼 예전 앱이 그대로 동작하는 변경. 이때는 v1에 더한다.
- 버전은 엔드포인트 단위로 올린다. API 전체를 v2로 복사하지 않는다.

### v1 쓰기를 지우는 시점

v2를 쓰는 앱 버전을 강제 업데이트 최소 버전으로 올린 뒤 지운다. 그 전까지 v1 쓰기는 버그 수정만 한다.

## 결과

- 예전 앱과 새 앱이 함께 동작한다. 서버를 먼저 배포해야 새 앱이 v2를 호출할 수 있다.
- 이미 저장된 사진은 촬영일이 비어 있다. 올린 사람 기기에 날짜가 남아 있으면 그 기록을 수정할 때 채워진다. S3 원본 EXIF로 일괄 채우는 일은 따로 정한다.
- 저장된 촬영일을 모르는 날짜로 되돌리는 경로는 없다. 사진을 지우고 다시 올리면 새 키라 비어 있다.
