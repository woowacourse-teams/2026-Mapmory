# ADR 0031. 서비스 수준 목표(SLO)를 정하고 알람 기준을 SLO에서 끌어낸다

- 상태: 제안
- 날짜: 2026-11-22
- 관련: #740, ADR 0001, ADR 0014, ADR 0018

## 문제

서비스 수준 목표가 없다. 그래서 알람 기준(5xx 1건, 5xx 비율 5%, 최소 요청 10건 등)이 근거 없이 정해져 있고, "얼마나 나빠야 사람을 깨우는가"에 답할 수 없다. ADR 0016은 "목표 응답 시간"을 말하지만 그 목표가 어디에도 없다.

지표를 들여다보니 SLO를 정할 때 조심할 점도 드러났다.

- **트래픽이 적다.** prod 3주(10/21~11/11, 22일) 요청은 14,453건, 하루 38~2,790건, 평균 약 660건(분당 약 0.5건)이다. 비율만 보면 몇 건으로도 크게 흔들린다.
- **앱이 계산하는 p95는 저트래픽에서 쓸 수 없다.** ADR 0014의 p95 Summary는 최근 몇 분의 요청으로 계산하고, 요청이 없는 구간은 0을 내보낸다. 3주 평균을 내면 0에 묻혀 0.1~1ms가 나오고, p95의 p95는 0이다.
- **앱 지표는 앱에 도착한 요청만 센다.** EC2·Nginx·인증서·DNS 장애로 요청이 못 들어오면 5xx도 0이라, 가장 큰 장애일수록 가용성이 100%로 보인다.
- **지표가 빈 기간이 있었다.** Agent가 Blue 관리 포트만 수집해 prod는 11/12~11/15 약 70시간 동안 앱 지표가 없었다(#741로 해결). 이 기간은 장애였는지 수집 공백이었는지 알 수 없다.
- **구조적 상한이 있다.** EC2 1대(Nginx + Blue/Green), RDS 단일 AZ가 직렬이다(ADR 0001). 카드 값으로 곱하면 약 99.7~99.8%이고, Blue/Green은 같은 EC2라 2중화로 치지 않는다.

### 측정값 (prod, 2026-10-21 ~ 2026-11-11)

5xx는 22일 동안 **0건**이었다.

지연은 0을 뺀 값으로 다시 쟀다. 평균은 `_sum ÷ _count`, 평소 p95는 0을 뺀 1분 p95들의 평균(`TM(0.000001:)`), 최악 p95는 1분 p95의 최댓값이다. p95는 Micrometer가 버킷으로 근사한 값이라 경계값(134, 352, 604ms 등)에 몰린다.

| API | 요청 수 | 평균 | 평소 p95 | 최악 p95 |
|---|---:|---:|---:|---:|
| GET 지도 요약 roots | 635 | 11ms | 13ms | 134ms |
| GET 기록 목록 | 984 | 28ms | 38ms | 317ms |
| GET 기록 상세 | 387 | 30ms | 36ms | 520ms |
| POST Presigned URL | 1,909 | 11ms | 20ms | 352ms |
| POST 기록 생성 | 242 | 223ms | 255ms | 2,080ms |
| PUT 기록 수정 | 13 | 119ms | 147ms | 352ms |
| POST 토큰 갱신 | 225 | 49ms | 51ms | 604ms |
| POST 카카오 로그인 | 11 | 51ms | 173ms | 906ms |

PUT 수정(13건)과 카카오 로그인(11건)은 표본이 적어 그룹으로 묶어 본다.

## 결정

### 1. SLI와 SLO

목표 기간은 30일(롤링)이다.

| 이름 | SLI (무엇을 재나) | SLO | 30일 허용량 |
|---|---|---|---|
| 가용성 | 밖에서 1분마다 `/health`를 부른 결과 중 성공 비율 | **99.5%** | 약 216분 |
| 서버 오류 | `/api/v1` 요청 중 5xx 비율 (4xx는 제외) | **≤ 0.5%** | 요청 약 2만 건 기준 약 100건 |
| 조회 지연 | 지도 요약·목록·상세·Presigned URL 요청 중 **300ms 안에 끝난 비율** | **99%** | |
| 저장 지연 | 기록 생성·수정 요청 중 **2초 안에 끝난 비율** | **99%** | |
| 인증 지연 | 로그인·토큰 갱신 요청 중 **1초 안에 끝난 비율** | **99%** | |

근거:

- **가용성 99.5%**: 구조적 상한(약 99.7~99.8%)보다 낮게 잡아, RDS 점검이나 EC2 장애 한 번은 견딘다. 99.9%(30일 43분)는 지금 구성으로 약속할 수 없다.
- **가용성은 외부 확인으로 잰다**: 앱 지표로는 앱에 도착하지 못한 요청이 보이지 않고, 저트래픽이라 밤에는 잴 요청이 없다.
- **조회 300ms**: 평소 p95가 13~38ms, 최악 p95가 134~520ms다. 평소보다 넉넉하고 최악의 대부분을 담는다. 앱을 열자마자 보는 화면이다.
- **저장 2초**: 평소 p95 255ms, 최악 p95 약 2.1초. 사진마다 S3 확인이 있고 그 재시도 상한이 3초다(ADR 0018).
- **인증 1초**: 외부(카카오·구글·애플) 호출이 들어간다. 최악 p95 906ms.
- **지연을 "기준 시간 안에 끝난 비율"로 재는 이유**: 요청을 하나하나 세므로 저트래픽에서도 0이 섞이지 않고, 30일 단위로 합산할 수 있다. p95 Summary는 구간마다 따로 계산돼 합산할 수 없다.

### 2. 측정 방식 (ADR 0014 보완)

- 지연 SLI는 SLO 전용 카운터 `http.server.requests.slo`(Prometheus `http_server_requests_slo_total`)로 잰다.
  - `http.server.requests`를 만드는 것과 같은 서버 요청 Observation을 받아, 요청이 끝날 때 한 번 센다. 같은 요청을 같은 시점에 센다.
  - 태그는 `uri`(경로 패턴), `method`, `outcome`, `le`다. `le`는 `0.3`, `1`, `2`, `+Inf` 가운데 요청 시간 이하인 모든 값에 1을 더하는 누적값이고(Prometheus `le`와 같은 뜻), `+Inf`는 전체 건수다.
  - `status`·`exception`·`version`·`slot`은 넣지 않는다. 시계열이 곱해지거나 배포마다 새로 생긴다.
- **Summary와 Histogram을 한 지표에 같이 둘 수 없어 SLO용 카운터를 따로 둔다.** `http.server.requests`에 SLO 경계(`management.metrics.distribution.slo`)를 붙이면 Micrometer Prometheus registry가 그 지표를 Histogram으로 바꾸고 p50·p95·p99 quantile을 내보내지 않는다(로컬에서 quantile 0개로 확인). 대시보드가 그 quantile을 쓴다. 또 CloudWatch Agent는 Prometheus Histogram을 버리고 Counter·Gauge·Summary만 받는다(ADR 0014).
- 기존 p95 Summary는 대시보드와 원인 분석용으로 그대로 둔다.
- 카운터를 CloudWatch Agent EMF 선언(`observability/cloudwatch/agent.json.tmpl`)에 추가한다. 차원은 `service, environment, method, uri, outcome, le`다.
- 외부 헬스체크는 Route 53 헬스체크(1분 간격)로 만들고, 그 지표로 가용성을 계산한다.

### 3. 오류 예산과 알람

소진 속도 = 지금 오류율 ÷ 허용 오류율(0.5%). 소진 속도 10이면 30일 예산을 3일 만에 쓴다.

**사람을 깨우는 알람 (증상)**

| 알람 | 조건 |
|---|---|
| 외부 헬스체크 실패 | 3분 연속 실패 |
| 5xx 건수 | 10분 안에 3건 이상. 저트래픽이라 비율 대신 건수로 본다 |
| 데드맨 (`metrics-missing`) | 앱 지표가 10분 동안 없음 (이미 있음) |

**Discord로만 보내는 알람 (예산이 새는 신호, 원인)**

| 알람 | 조건 |
|---|---|
| 5xx 비율 | 1시간 동안 요청 30건 이상이고 5xx 비율 > 5% (소진 속도 10) |
| 조회 지연 | 1시간 동안 조회 요청 30건 이상이고 300ms 초과 비율 > 5% |
| 저장 지연 | 1시간 동안 저장 요청 10건 이상이고 2초 초과 비율 > 10% |
| 기존 5xx 1건 알람, 커넥션 대기, EC2·RDS 자원 | 그대로 |

- 기존 `mapmory-<env>-api-5xx-ratio`(분당 10건 이상일 때만 계산)는 prod 평균이 분당 0.5건이라 사실상 항상 0이다. 위 1시간 기준으로 바꾼다.
- 기준값은 `observability/cloudwatch/alarms.sh` 맨 위 변수로 모은다.

### 4. 오류 예산 정책

- 30일 예산의 50%를 쓰면 다음 스프린트에서 원인 작업을 기능 작업보다 먼저 한다.
- 예산을 다 쓰면 긴급 수정 외의 prod 배포를 멈추고 회고한다.
- 위 두 줄은 팀 합의가 필요하다.

### 5. 검토

- 매달 첫 주에 지난 30일 SLI를 보고 목표를 그대로 둘지 정한다.
- 11/12~11/15처럼 지표가 빈 기간은 SLI 계산에서 빼고, 빈 시간을 함께 적는다.

## 고려한 대안

- **가용성 99.9%**: 지금 구성(EC2 1대, RDS 단일 AZ)의 상한보다 높다. Multi-AZ·다중 EC2를 도입할 때 다시 본다.
- **`http.server.requests`에 SLO 경계를 붙인다(`management.metrics.distribution.slo`)**: 그 지표가 Histogram이 되어 p50·p95·p99 quantile이 사라지고(대시보드가 깨짐), CloudWatch Agent는 Histogram을 버려 버킷도 CloudWatch에 오지 않는다. SLO 전용 카운터를 따로 둔다.
- **p95 Summary로 지연 SLO를 잰다**: 저트래픽에서 요청 없는 구간이 0으로 나와 쓸 수 없고, 30일 합산도 안 된다.
- **요청 기준 가용성만 쓴다**: 앱에 도착하지 못한 요청이 보이지 않는다. 서버 오류 SLI로는 남긴다.
- **5xx 비율 알람만 쓴다**: 저트래픽이라 비율이 몇 건에 흔들리거나, 최소 요청 조건 때문에 아예 계산되지 않는다. 건수 알람을 함께 둔다.

## 결과

- 알람 기준을 SLO에서 계산해 설명할 수 있다("5%는 소진 속도 10").
- 밤이나 트래픽이 없을 때도 가용성을 잴 수 있다.
- SLO 카운터와 외부 헬스체크로 사용자 지정 지표가 몇 개 늘어난다(월 몇 달러 수준). Route 53 헬스체크는 월 약 1달러.
- 측정값이 3주·저트래픽 기준이라, 첫 두 달은 목표를 조정할 가능성이 높다.
