# 영상 생성 알림: 기기 등록 설계

- 날짜: 2026-10-29
- 상태: 기기 등록·해제 Java 코드 반영 및 관련 테스트 20개 통과. 영상 알림 전체 구현·배포는 아직 진행하지 않았다.
- 구현: [#545](https://github.com/woowacourse-teams/2026-Mapmory/issues/545)
- 후속 리팩토링: [#553](https://github.com/woowacourse-teams/2026-Mapmory/issues/553)
- 결정 배경: [ADR 0025](adr/0025-share-video-notification-registration.md)

## 확정한 범위

- 기존 `PushToken` 엔티티와 `push_token` 스키마를 유지한다.
- 설치 UUID·활성 상태·연결 버전·JPA 버전 컬럼은 이번 단계에 추가하지 않는다.
- 영상 생성 요청 기기만 알림 대상으로 삼는다.
- 로그아웃하면 이전 연결의 영상 알림을 취소하는 정책을 따른다. 앱 백그라운드 전환·일반 종료는 로그아웃이 아니다.
- 성공 알림을 먼저 구현하고 생성 실패 알림을 후속 구현한다.
- 영상 완료와 알림 이벤트는 같은 트랜잭션에 Outbox로 저장한다. Outbox 상세 설계·마이그레이션·발송 워커는 별도 단계다.

## 변경 전 구현 기준

- `PUT /api/v1/push-tokens`: 회원·FCM 토큰·플랫폼 등록, 변경 전 응답 204.
- `DELETE /api/v1/push-tokens`: 로그인 회원에게 속한 토큰만 삭제, 변경 전에는 token을 본문으로 받음.
- 변경 전에는 같은 토큰으로 다른 회원이 등록하면 기존 행의 소유 회원을 변경했다.
- 앨범 알림은 커밋 후 메모리 이벤트와 비동기 실행기를 사용한다. 실제 FCM 구현 없이 `LoggingPushSender`가 로그만 남긴다.
- 인증 로그아웃은 refresh token을 폐기한다. 기기 토큰 삭제와 자동으로 연결되어 있지 않다.

## 제안 API 계약

아래 계약을 로컬 코드에 반영했다. 실제 배포 환경 반영 여부는 확인하지 않았다.

### 등록

`PUT /api/v1/push-tokens`

```json
{"token":"<FCM token>","platform":"ANDROID"}
```

- 요청 본문과 로그인 인증은 기존 계약을 유지한다.
- 응답은 204에서 200으로 바꾸고 기존 `ApiResponse`로 등록 ID를 반환한다.

```json
{"data":{"pushTokenId":42}}
```

- 같은 회원·같은 토큰: 같은 행 ID 유지, 플랫폼 갱신.
- 다른 회원·같은 토큰: 기존 행을 삭제·flush하고 새 행을 저장한다. 기존 행 ID를 새 회원에게 재사용하지 않는다.
- 삭제·재생성은 한 트랜잭션에서 수행하므로 새 등록 실패 시 기존 등록 삭제도 롤백한다.
- 기존 행은 비관적 쓰기 잠금으로 직렬화한다. 없는 행에 대한 동시 최초 등록은 UNIQUE 제약으로 보호하며 충돌은 트랜잭션 밖에서 409로 변환한다.
- 잠금 충돌은 409로 반환한다. 서버에서 위반된 트랜잭션을 그대로 재사용하지 않는다.
- 앱은 충돌 후 짧은 지연을 두고 제한된 횟수만 등록 재시도한다. 무한 재시도하지 않는다.

### 해제

`DELETE /api/v1/push-tokens`

```json
{"pushTokenId":42}
```

- 로그인 회원과 ID가 모두 일치하는 행만 삭제한다.
- 이미 없거나 다른 회원의 ID여도 204로 응답한다.
- FCM 토큰 문자열 대신 등록 ID를 사용해 이전 등록의 지연된 삭제가 새 등록을 지우는 것을 줄인다.
- 앱은 등록 응답 ID를 로그인 자격 정보와 함께 보관하고 해제 성공 후 제거한다.
- 재로그인 등록 요청과 이전 로그아웃 해제 요청은 앱에서 순서대로 처리한다.
- 구버전의 token 기반 해제 요청은 새 계약과 다르다. 배포 전 클라이언트 사용처를 확인하고 동시 전환 또는 별도 버전 API를 결정한다. 서버만 먼저 바꾸지 않는다.

## 왜 token 대신 pushTokenId로 해제하는가

`token`은 FCM이 메시지를 전달할 주소이고, `pushTokenId`는 특정 시점에 생성된 등록 행의 PK다.
FCM 토큰을 ID로 바꾸거나 없애는 것이 아니다. 등록·발송에는 계속 token이 필요하고, 해제 대상 지정에는 등록 ID를 사용한다.

### 등록 ID를 응답하는 이유

등록 성공 시 앱이 받은 `pushTokenId=42`를 저장한다. 이후 해제 요청과 영상 생성의 수신 대상 지정에 이 ID를 사용한다.
서비스는 엔티티를 반환하고 Controller는 ID만 DTO로 변환한다. FCM 토큰·회원 ID 등 전체 엔티티를 그대로 응답하지 않는다.
ID는 인증 수단이 아니며 서버는 항상 로그인 회원의 소유인지 검증한다.

### 해제 성공 후 재등록과 지연된 중복 해제 예시

1. 회원 A가 FCM 토큰 T를 등록해 등록 ID 42를 받는다.
2. 앱이 42의 해제를 요청한다. 서버에서 삭제가 성공했지만 앱이 응답을 받지 못한다.
3. 앱이 보낸 해제 재시도 요청이 네트워크에서 지연된다.
4. A가 T를 다시 등록해 새 ID 43을 받는다.
5. 3번의 지연된 해제 재시도 요청이 서버에 도착한다.

| 해제 조건 | 결과 |
| --- | --- |
| memberId=A, token=T | 새 등록 43도 같은 회원·같은 토큰이므로 삭제될 수 있음 |
| memberId=A, pushTokenId=42 | 42는 이미 없으므로 아무것도 삭제하지 않고 43은 유지 |

이 효과는 먼저 등록 42의 삭제가 성공해 새 등록 43이 만들어졌다는 전제가 필요하다.
첫 해제 자체가 아직 실행되지 않았고 같은 회원의 재등록이 기존 42를 재사용하면 ID만으로 요청 순서를 구분하지 못한다.
또한 같은 설치본의 토큰 갱신과 로그인 세대 구분은 ID만으로 해결하지 않는다. 이 한계는 #553에서 다룬다.

## 왜 등록 트랜잭션을 TransactionTemplate로 감싸는가

### 하나의 트랜잭션으로 보호할 범위

기존 등록 잠금 조회 → 같은 회원이면 갱신 → 다른 회원이면 기존 행 삭제 → 새 등록 저장을 하나로 묶는다.
새 저장이 실패했을 때 기존 행 삭제만 남으면 안 되므로 전부 커밋하거나 전부 롤백한다.
`flush()`는 SQL을 DB에 반영하지만 커밋하지 않는다. DELETE를 먼저 flush하는 이유는 같은 token의 INSERT가 기존 UNIQUE 값과 충돌하지 않도록 실행 순서를 정하기 위해서다.

### 실행 범위와 오류 변환 범위를 분리

```text
register(): 트랜잭션을 감싸는 공개 메서드
  try
    registrationTransaction.execute(...)
      트랜잭션 시작
      registerInTransaction(): 실제 등록 로직
      성공하면 커밋 / 실패하면 롤백
  catch
    토큰 UNIQUE 위반·잠금 충돌을 BusinessException으로 변환
    공통 예외 처리기가 409 응답 생성
```

제약 위반은 flush뿐 아니라 커밋 시점에도 드러날 수 있다. `@Transactional register()` 본문 안의 try/catch는
Spring 프록시가 메서드 반환 후 수행하는 커밋 예외까지 잡지 못한다.
`execute()` 전체를 try/catch로 감싸면 등록 트랜잭션의 실행·커밋·롤백을 포함하는 범위에서 오류를 다룰 수 있다.
단순히 BusinessException으로 변환하기 위해 반드시 프로그래밍 방식 트랜잭션이 필요한 것은 아니다.
여기서는 트랜잭션 종료 후 오류 분류라는 경계를 코드 한 곳에서 명확히 표현하려고 사용한다.

private `registerInTransaction()`에 `@Transactional`만 붙이고 같은 객체에서 호출하는 방식은 사용하지 않는다.
기본 프록시 방식의 자기 호출은 트랜잭션 어노테이션을 적용하지 못한다. 이 설계에서는 private 메서드를 `execute()` 내부에서 직접 호출한다.
TransactionTemplate 객체를 생성·설정하는 것만으로 트랜잭션이 시작되는 것은 아니다. 반드시 `execute()`로 실행해야 한다.

### REQUIRES_NEW를 선택한 이유와 비용

- 현재 Controller 직접 호출 경로에는 외부 트랜잭션이 없어 기본 REQUIRED도 등록 트랜잭션을 시작할 수 있다. REQUIRES_NEW가 지금 경로의 필수 조건은 아니다.
- 제안 코드는 향후 다른 트랜잭션에서 호출해도 등록 단위의 커밋·롤백을 execute() 안에서 끝내기 위해 REQUIRES_NEW를 사용한다.
- 외부 트랜잭션이 있다면 잠시 중단하고 독립 트랜잭션을 실행한다. 등록 성공 후 외부 작업이 롤백돼도 등록은 되돌아가지 않는다.
- 외부 트랜잭션이 자원을 보유한 채 추가 DB 커넥션을 요구할 수 있으므로 커넥션 풀과 잠금 경합을 고려해야 한다.
- 이 설정은 독립적인 기기 등록 API에 한정한다. 영상 완료와 Outbox 이벤트 저장에 REQUIRES_NEW를 각각 적용하면 원자성이 깨지므로 그 둘은 같은 트랜잭션으로 처리한다.

### 구체적인 실패 예시

두 요청이 처음 보는 token=T를 동시에 등록하려고 한다. 빈 조회 결과에 대한 잠금 동작은 DB 격리 수준과 인덱스에 따라 달라질 수 있다.
UNIQUE 제약으로 중복 행이 저장되지 않도록 하고, 패자는 토큰 제약 위반 또는 잠금 충돌로 실패할 수 있다.
실패 트랜잭션을 종료한 뒤 토큰 제약 위반인지 판별하고 409로 반환한다. 다른 무결성 위반은 그대로 전달해 원인을 숨기지 않는다.
서버가 실패한 트랜잭션 안에서 재시도하지 않으며 앱이 제한된 재시도 정책을 적용한다.

### 검토한 대안

- 별도 빈의 `@Transactional` 메서드를 비트랜잭션 facade가 호출하고 밖에서 예외 처리: 같은 목적을 달성할 수 있다. 클래스 분리가 필요하다.
- `@Transactional` 메서드에서 예외를 변환해 다시 던짐: 실행 중 오류의 롤백은 가능하지만 메서드 반환 이후 커밋 오류까지 본문에서 분류하지 못한다.
- 전역 예외 처리기에서 모든 DataIntegrityViolationException을 409로 변환: 토큰 등록과 무관한 제약 오류까지 숨길 수 있어 선택하지 않는다.

## 요청 기기와 영상 작업 연결: 다음 단계의 입력

- 영상 요청은 선택적인 `pushTokenId`를 받는 안으로 설계한다. 없으면 영상 생성만 수행한다.
- 서버는 로그인 회원이 소유한 등록 ID인지 검증한다. 다른 회원의 행 ID만 알아서는 연결할 수 없다.
- 요청 시 확인한 등록 ID를 작업별로 보존해야 한다. 기존 PushToken 엔티티는 변경하지 않는다. 작업별 연결의 저장 위치와 스키마는 다음 단계에서 정한다.
- Outbox에는 요청 당시 회원 ID와 등록 ID를 보존한다. 완료 시 회원의 전체 토큰을 조회해 대상을 다시 선택하지 않는다.
- 발송 직전 해당 ID의 행이 존재하고 소유 회원이 요청 당시 회원과 같은지 확인한다. 탈퇴 회원에게 발송하지 않는다.
- 행이 사라지면 대상 없음으로 발송을 생략한다. 같은 토큰 값으로 새 행이 생겨도 과거 알림을 옮기지 않는다.
- 행 삭제가 허용되므로 작업·Outbox에서 삭제를 차단하는 단순 FK나 연쇄 삭제를 사용하지 않는다. 참조 무결성 정책은 Outbox 설계 단계에서 정한다.

## 수명주기 예시

1. 회원 A가 토큰 T를 등록해 ID 42를 받는다.
2. 영상 요청은 ID 42를 수신 대상으로 선택한다.
3. 로그아웃 전에 ID 42의 해제 API가 성공한다.
4. 같은 회원 또는 다른 회원이 T를 재등록하면 새 ID 43을 받는다.
5. 과거 영상의 수신 대상은 42이므로 43으로 발송하지 않는다.

## 현재 구조의 한계

- FCM 토큰 T1이 T2로 바뀌어도 같은 설치본인지 알 수 없다. 과거 작업의 T1 등록을 T2로 자동 이동하지 않는다.
- 토큰 갱신 시 앱이 이전 등록 ID를 알고 있다면 해제 후 새 등록을 수행한다. 기존 작업의 알림은 취소될 수 있다.
- 등록 해제가 실패하면 서버는 로그아웃을 알지 못한다. 같은 회원이 해제 없이 재등록하면 기존 ID를 유지할 수 있다. 인증 로그아웃만으로 취소가 보장된다고 설명하지 않는다.
- 과거 access token으로 지연된 등록 요청이 도착하면 오래된 계정으로 다시 등록될 수 있다. 설치본·로그인 세대 식별은 #553에서 다룬다.
- 발송 대상 확인 직후 로그아웃되거나 FCM에 이미 접수된 메시지는 회수할 수 없다.
- 기존 `PushSender`의 무효 토큰 문자열만으로 삭제하는 방식은 지연 응답과 새 등록을 구분하지 못한다. FCM 발송 구현 시 등록 ID를 포함한 결과 매핑을 설계한다.
- 재등록 시 삭제되는 행을 기존 앨범 알림이 조회 중일 수 있다. 계정 변경과 발송의 경쟁 조건을 실제 FCM 연동 단계에서 검증한다.

## 구현 시 검증할 항목

- 같은 회원 재등록 시 ID 유지, 다른 회원 등록 시 ID 변경과 총 행 수 유지.
- 해제 후 같은 토큰 재등록 시 새 ID 발급, 옛 ID 해제로 새 행이 삭제되지 않음.
- 다른 회원 ID 삭제 불가, 탈퇴 회원 등록 불가.
- 삭제 후 새 저장 실패 시 전체 트랜잭션 롤백.
- 동시 최초 등록과 소유 회원 변경 경쟁 시 중복 행이 없고 충돌이 409로 응답됨.
- 기존 앨범 알림과 토큰 등록·해제 테스트 호환성.
- 클라이언트 등록 응답 ID 저장, 해제 순서, 제한된 재시도.

- 전체 백엔드 테스트·지속적인 동시 요청 부하·FCM 발송·클라이언트 기기 수신은 검증하지 않았다. 동시성 통합 검증은 같은 토큰에 대한 동시 최초 등록 2건으로 한정한다.
