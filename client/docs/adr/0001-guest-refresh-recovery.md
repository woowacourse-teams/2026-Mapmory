# ADR 0001: 게스트 토큰 갱신을 세션이 소유하고 복구 가능한 실패를 제한적으로 재시도한다

- 상태: 채택 (PR #438 구현, 실서버·실기기 검증은 별도)
- 날짜: 2026-10-23
- 범위: Android/iOS 공통 게스트 인증 및 플랫폼 토큰 저장소
- 관련: [기존 게스트 보존 결정](../guest-session-recovery.md), [트러블슈팅](../troubleshooting/guest-refresh-response-loss.md), [PR #438](https://github.com/woowacourse-teams/2026-Mapmory/pull/438), [서버 PR #441](https://github.com/woowacourse-teams/2026-Mapmory/pull/441)

## 배경

게스트 기록은 회원 ID에 귀속되며, 토큰을 잃으면 다시 로그인할 수단이 없다. 서버가 refresh token A를 폐기하고 B를 발급한 뒤 응답이 유실되면 앱에는 A만 남는다. 기존 서버는 A 재전송을 탈취로 판단해 후속 토큰까지 폐기했다. 저장소 읽기 오류를 토큰 부재로 처리하거나, B 저장 실패 후 A를 재사용하는 경우도 신원 유지에 위험하다.

## 결정

1. **토큰 부재와 저장소 장애를 구분한다.** `AuthTokenStore.read()`의 non-null wrapper와 오류 전달 경계로 Swift에서도 둘을 구분한다. iOS Keychain은 `errSecItemNotFound`만 부재로 취급한다. 읽기 실패 때 신규 게스트를 생성하거나 기록 캐시를 지우지 않는다. 과거 UserDefaults fallback의 토큰은 우선 복원하되 새 저장 실패에 평문 fallback을 추가하지 않는다.
2. **발급받은 토큰을 먼저 메모리에 보존한다.** 저장 실패 시 `pendingPersistence`로 표시하고 다음 요청에서 저장만 재시도한다. 이미 소비한 이전 refresh token으로 돌아가지 않는다. 저장 성공 전까지 인증 성공으로 처리하지 않는다.
3. **인증 작업의 수명은 세션이 소유한다.** `SupervisorJob` 기반 scope와 진행 중인 `Deferred`로 작업을 공유한다. 초기 인증과 특정 access token의 401 복구를 구분하고, 인증 상태 변경과 실제 갱신은 `authenticationMutex`로 직렬화한다. 화면 호출자의 취소가 회전 응답 수신과 저장을 중단하지 않게 한다.
4. **실패를 분류해 재시도를 제한한다.** 연결 오류와 5xx는 1초·2초 대기로 최대 3회 시도한다. 실패 후 60초 동안 요청을 제한하고 다음 요청에서 복구한다. 수동 요청도 같은 제한을 따른다. `INVALID_REFRESH_TOKEN`, `EXPIRED_REFRESH_TOKEN`은 세션 내 자동 갱신을 중단한다. 토큰과 캐시는 보존한다.
5. **취소는 소유자별로 처리한다.** 호출자 취소는 해당 호출자에게 전파한다. 세션이 살아 있는 동안의 내부 갱신 취소는 인증 잠금 안에서 일반 오류와 60초 제한을 함께 기록한다. worker Context 자체가 취소돼 결과를 반환하지 못하면 살아 있는 대기자는 기록된 일반 실패를 받는다. 컨테이너 종료는 세션 scope를 취소하고 후속 작업 생성을 거부한다.

## 서버 계약과 출시 전제

`backend-develop`의 `c1a2d358` 기준으로 확인했다.

- `POST /api/v1/auth/token/refresh`: 요청은 `refreshToken`, 응답은 `data.accessToken`과 `data.refreshToken`이다.
- 게스트의 폐기된 토큰은 후속 ID가 있고 후속 토큰이 미폐기·미만료일 때만 재발급한다. 이전 토큰의 후속 참조도 갱신해 연속 응답 유실을 복구한다.
- 후속 refresh가 이미 회전됐거나 로그아웃·만료된 경우 복구하지 않는다. 소셜 회원에는 이 예외가 없다.
- 여기서 미사용은 후속 refresh가 회전에 사용되지 않았다는 의미다. access token으로 보호 API를 호출했는지는 판단 기준이 아니다.
- 서버 코드와 V29 배포가 클라이언트 출시보다 선행해야 한다. 서버 계약 없이 이전 토큰을 재시도하면 기존 전체 폐기 정책을 유발할 수 있다.

## 검토한 대안

- 실패를 프로세스 종료까지 고정: 일시적인 오프라인도 앱 전체 인증 불능으로 이어져 배제했다.
- 제한 없는 재시도: 응답 유실 이후 반복 전송과 서버 부하를 막지 못해 배제했다.
- 호출자 scope에서 갱신: 화면 취소가 회전 응답과 저장을 끊을 수 있어 배제했다.
- 취소 예외를 공유 실패로 저장: 다른 기록 저장까지 취소시켜 실패 UI로 전환하지 못할 수 있어 배제했다.
- 새 게스트 자동 생성: 기존 기록의 소유권을 복구하지 못하므로 배제했다.
- 짧은 서버 유예 시간만 적용: PDF 사례처럼 11시간 후 재시도하는 경우를 다루지 못한다. 서버 후속 토큰 확인과 앱 재시도 제어를 함께 사용한다.

## 결과와 한계

저장소 장애, 화면 취소, 일시적 네트워크 실패를 기존 게스트의 소실로 처리하지 않는다. 복구 가능한 실패도 최대 60초 동안 수동 재시도가 제한될 수 있다. 새 토큰 저장 전 프로세스 종료는 메모리만으로 보호할 수 없으므로 서버 복구에 의존한다.

이미 전체 폐기된 계정과 과거 회전 관계가 없는 토큰은 소급 복구하지 않는다. V29는 nullable 컬럼을 추가할 뿐 과거 관계를 채우지 않는다. 재설치 복구, 소셜 로그인 연결, 영구 복구 수단은 이 결정의 구현 범위 밖이다.

검증 결과와 남은 통합 검증은 [트러블슈팅 문서](../troubleshooting/guest-refresh-response-loss.md)에 기록한다.
