# 도메인 및 비즈니스 규칙 점검

기준: 현재 `shared` 도메인·화면 상태·API 계약 대조

## 요약

현재 여행 기록의 날짜 검증과 기본 CRUD 흐름은 일부 구현되어 있다.
반면 태그, 미디어 제약, 통계, 지도 방문 데이터는 화면 또는 문서 수준에만 있고
도메인과 API 계약으로 연결되지 않았다.

## 우선순위가 높은 불일치

| 항목 | 현재 상태 | 문제 | 규칙 소유자 | 우선순위 |
| --- | --- | --- | --- | --- |
| 날짜 | `TripRecordDraft.dateValidationError()`가 날짜 형식과 역전만 확인 | 종료일만 입력하는 경우를 허용하고, 시작일만 입력했을 때 종료일을 시작일로 정규화하지 않음 | 백엔드 최종 검증, 클라이언트 사전 검증 | 높음 |
| 기록 지역 | API 문서상 `DISTRICT`만 허용 | `TripRecordDraft`는 `locationId`만 가지고 있고 Fake Repository도 지역 타입을 검증하지 않음 | 백엔드 최종 검증, 클라이언트 UX 검증 | 높음 |
| 제목 정책 | API 계약은 빈 문자열·공백을 허용 | 기록 작성 화면은 제목이 비어 있으면 저장을 막음 | API와 화면 정책 중 하나로 합의 필요 | 높음 |
| 태그 | 지도·일지 화면에서 문자열 목록만 관리 | 기록 모델·요청 DTO·조회 쿼리에 태그가 없어 실제 저장·필터링이 되지 않음 | 백엔드 계약 후 공통 도메인 | 높음 |

## 추가로 필요한 도메인 또는 정책

### 1. 태그

현재 화면의 `전체`, `가족`, `애인`, `친구`, `혼자`는 UI 문자열이다.

결정해야 할 내용:

- 한 기록에 태그 하나만 선택하는지, 여러 개를 선택하는지
- 태그 없이 저장할 수 있는지
- 태그를 수정할 수 있는지
- 목록·지도 필터가 서버 조회 조건인지, 이미 받은 기록의 클라이언트 필터인지
- 태그를 고정 enum으로 둘지, 서버가 관리하는 목록으로 둘지

현재 화면은 단일 선택처럼 보이지만, 이것만으로 API 계약을 확정하면 안 된다.
백엔드와 합의한 뒤 `TripTag`와 `TripRecord`의 태그 필드, 요청·응답 DTO, `TripRecordQuery`를 함께 설계한다.

### 2. 지역 선택

현재 `Location`은 `id`, `countryId`, `parentId`, `regionCode`, `name`, `type`을 가진다.
다음 불변식을 명시해야 한다.

- 여행 기록은 최종 선택 단계인 `DISTRICT`만 참조한다.
- `DISTRICT`의 `parentId`는 같은 국가의 `PROVINCE`를 가리킨다.
- 지도 Polygon의 canonical `regionCode`와 `Location.regionCode`가 일치한다.
- 지도에 표시된 지역명과 기록 작성 화면에 전달되는 `Location`이 일치한다.

지도와 서버의 코드는 백엔드가 최종 권위자로 검증하고, 클라이언트는 저장 전에 사용자에게 오류를 보여주는 역할을 한다.

### 3. 미디어

`TripRecordMedia`와 `objectKeys`는 존재하지만 다음 정책이 API 계약에 완전히 고정되지 않았다.

- 허용 MIME 타입
- 파일당 최대 크기
- 기록당 최대 사진 수
- 한 기록에서 같은 `objectKey`를 중복 첨부할 수 있는지
- 수정 시 제거된 객체를 언제 삭제하는지
- 기록 삭제 시 S3 객체와 백업 데이터를 함께 삭제하는지
- `sortOrder`의 시작값과 중복 허용 여부

업로드 완료된 `objectKey`만 기록 요청에 포함한다는 규칙은 이미 확정되어 있다.
나머지는 서버가 검증하고 클라이언트는 같은 제약을 미리 안내해야 한다.

### 4. 통계

`TripStatisticsUiState`는 있지만 통계 API와 집계 규칙은 확정되지 않았다.

최소한 다음 기준이 필요하다.

- 방문 국가 수: 기록이 있는 고유 국가 수인지
- 방문 지역 수: 고유 `Location` 수인지, 기록 수인지
- 기록 수: 삭제되지 않은 현재 회원의 기록 수인지
- 사진 수: 업로드 성공한 미디어 수인지
- 기간 필터와 전체 기간의 기준
- 같은 지역에 여러 기록을 작성했을 때의 집계 방식

### 5. 회원과 권한

`MemberSummaryDto`와 `TripRecordData.memberId`는 있지만 회원 도메인·세션 도메인은 없다.
현재 `X-Member-Id`를 Repository 생성자에 주입하고, 인메모리 컨테이너 기본값으로 `1L`을 사용한다.

이는 로그인 전 MVP의 임시 계약으로 유지할 수 있다. 다만 로그인 도입 시 다음을 별도 도메인으로 분리해야 한다.

- 로그인 세션과 현재 회원
- Access Token 보관·갱신
- 기록 조회·수정·삭제 권한
- 회원 탈퇴와 기록·미디어 삭제 정책

### 6. 시간과 식별자

- `startDate`, `endDate`는 여행 날짜이므로 날짜만 저장한다.
- `createdAt`, `updatedAt`의 문자열 형식과 시간대(UTC 등)를 API 계약에 명시한다.
- 서버가 발급한 기록 ID를 사용하고, 레거시 `TripRecord`의 무작위 ID 생성 방식은 API 모델과 섞지 않는다.

## 현재 중복 모델

현재 다음 두 여행 기록 모델이 함께 존재한다.

- `com.mapmory.shared.domain.TripRecord`: 이미지 한 장, 문자열 장소, 무작위 ID를 사용하는 기존 모델
- `com.mapmory.shared.domain.model.TripRecordData`: `locationId`, 여러 미디어, 회원 ID를 포함하는 현재 API 모델

실제 Repository와 ViewModel 흐름은 `TripRecordData`를 사용하고, 기존 모델은 레거시 테스트와 UI 변환 코드에 남아 있다.
새 기능은 `TripRecordData` 계열에만 추가하고, 레거시 모델의 사용처를 정리한 뒤 제거 여부를 별도 작업으로 결정한다.

## 다음 작업 순서

1. 날짜 규칙을 코드와 테스트에 맞춘다: 종료일 단독 입력 거부, 시작일 단독 입력 정규화.
2. 기록 저장 전 `DISTRICT` 지역 검증을 추가한다.
3. 제목 빈 값 정책을 API와 화면 중 하나로 통일한다.
4. 백엔드와 태그·미디어 제약·통계 집계 규칙을 합의한다.
5. 합의된 항목만 도메인 모델과 DTO에 추가한다.

태그·통계·인증은 API 계약이 확정되기 전 클라이언트가 임의로 도메인을 만들지 않는다.
