# 게스트 로그인 만료: 응답 유실과 인증 취소 처리

## 증상과 원인

제공된 「개발서버-로그인-만료-원인.pdf」는 서버 회전 후 응답 유실, 약 11시간 뒤 이전 refresh 재전송, 재사용 감지에 의한 전체 폐기와 15초 간격의 반복 실패를 설명한다. 이 기록은 제공된 분석 자료의 내용이며, 이번 PR 리뷰에서 운영 로그나 DB를 다시 조회한 결과는 아니다.

문제의 핵심은 앱이 새 토큰을 받지 못했다는 사실과 서버가 이미 이전 토큰을 폐기했다는 사실이 동시에 성립한다는 점이다. 새 게스트를 만들면 기존 기록의 접근권은 회복되지 않는다.

## 변경 내용

| 변경 위치 | 변경 및 목적 |
| --- | --- |
| `AuthSession.kt` | 저장소 오류 구분, 새 토큰 메모리 보존, 세션 소유 공유 작업, 실패 분류와 재시도 제한, 취소 격리 |
| `AndroidAuthTokenStore.kt` | 손상된 저장값을 토큰 부재로 취급하지 않고 오류로 전달 |
| `KeychainAuthTokenStore.swift` | Keychain 조회 오류 전달, 과거 fallback 우선 복원, 새 저장 실패를 명시적으로 전달 |
| `AppContainer.kt` | 읽기 실패 시 기록 캐시 보존, 컨테이너 종료 시 인증 scope 종료 |
| 인증·백그라운드 저장 테스트 | 실패 후 복구, 취소 격리, 저장 상태 전환과 반복 호출 제한 검증 |

## 트러블슈팅 과정

### 1. 저장 실패 방어만으로는 응답 유실을 해결하지 못함

갱신 응답을 받은 뒤 저장이 실패하는 경우에는 새 토큰을 메모리에 유지하고 저장만 재시도하도록 했다. 하지만 응답 자체를 못 받은 경우에는 새 토큰이 메모리에도 없다. 서버 PR #441의 후속 토큰 확인 복구와 결합하는 것으로 해결 범위를 정했다.

### 2. 모든 갱신 실패를 영구 고정하면 일시 장애가 지속 장애가 됨

초기 구현은 같은 토큰의 반복 전송을 막기 위해 실패를 프로세스 수명 동안 보관했다. 오프라인에서 한 번 실패하면 네트워크 복구 후에도 인증 요청이 차단됐다. 연결 오류·5xx의 제한된 재시도와 60초 후 재시도로 변경했고, 무효·만료 토큰만 자동 갱신 중단 대상으로 남겼다.

### 3. 이전 요청의 취소가 새 기록 저장까지 취소함

`CancellationException`을 공유 실패로 보관하면 `observeOperation()`이 이를 다시 던지고, 백그라운드 저장이 일반 실패 처리 없이 끝나 `SAVING`에 남을 수 있었다. 호출자와 공유 작업의 수명을 분리하고 내부 취소는 일반 인증 실패로 전달하도록 했다.

### 4. 내부 취소를 일반 오류로 바꾸는 것만으로는 반복 호출을 막지 못함

중간 구현에서는 내부 취소 시 `blockedFailure`와 `retryAt`이 기록되지 않아 연속 21회 요청이 refresh 21회로 이어졌다. 최신 구현은 `authenticationMutex` 안에서 일반 실패와 60초 제한을 함께 기록한다. Context 자체가 취소된 worker는 값을 반환하지 못할 수 있으므로 살아 있는 대기자가 기록된 실패를 읽도록 했다. 실제 세션 종료는 취소를 유지하고 후속 작업을 거부한다.

## 검증

코드 기준: PR #438의 `d6e46e0c`. 별도 추출 사본에서 `./gradlew :shared:jvmTest`를 실행해 **352개 통과, 실패·오류·스킵 0개**를 확인했다.

- 내부 취소 예외 및 worker Context 취소 모두에서 반복 21개 요청의 초기 인증·401 경로가 추가 refresh를 보내지 않는다.
- 주입 시계 59,999ms에는 차단하고 60,000ms에는 정상 복구·토큰 저장한다.
- 호출자 취소에도 다른 대기자와 토큰 저장이 성공한다.
- `observeOperation()`과 `BackgroundTripRecordSaver`를 통한 내부 취소가 `FAILED` 상태로 끝난다.
- 세션 종료 시 진행 중 작업이 종료되고 후속 21회 요청이 추가 갱신을 만들지 않는다.
- 저장소 읽기 실패 시 신규 게스트를 만들지 않고, 회전 토큰 저장 실패 시 이전 refresh를 재사용하지 않는다.

Android/iOS Kotlin 컴파일 및 Swift 타입 검사 성공은 기존 PR 구현 검증에 기록되어 있다. 이번 문서 작성에서는 다시 실행하지 않았다. 원격 CI는 커밋별 결과를 확인해야 하며, 위 JVM 결과가 실기기·실서버 동작을 보장하지는 않는다.

## 출시 전 확인과 잔여 한계

1. 대상 서버에 PR #441의 복구 코드와 V29가 실제 배포됐는지 확인한다.
2. 테스트용 게스트로 회전 커밋 뒤 응답만 유실시키고, 앱 재시도 및 프로세스 재시작 뒤 동일 회원으로 복구되는지 확인한다. 연속 응답 유실도 포함한다.
3. Android/iOS 실기기에서 화면 취소, 네트워크 복구, 저장 실패와 실패 UI를 확인한다.
4. 이미 잠긴 계정과 V29 이전의 연결 정보 없는 토큰은 자동 복구 대상으로 간주하지 않는다.

실서버 응답 유실 실험, 실제 배포 상태, 실기기 검증은 이번 리뷰에서 수행하지 않았다. 위 항목은 완료된 검증이 아니다. 실제 토큰이나 서버 접속 자격 증명은 문서와 로그에 남기지 않는다.
