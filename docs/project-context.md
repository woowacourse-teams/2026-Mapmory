# Mapmory 프로젝트 컨텍스트

이 문서는 긴 대화에서 반복해서 설명할 필요가 있는 프로젝트 방향, 사용자 선호, 현재 진행 맥락을 다음 Codex 세션에 전달하기 위한 요약이다. 대화 전문이나 원본 증거를 대신하지 않는다. 날짜가 붙은 수치와 작업 상태는 과거 기준일의 정보일 수 있으므로, 이어서 실행하기 전에 현재 상태를 확인한다.

## 새 세션에서 먼저 확인할 것

1. 이 문서를 읽고 사용자가 이미 정정한 내용이나 완료한 문서를 다시 처음부터 요구하지 않는다.
2. 저장소의 현재 브랜치, 변경 사항, GitHub PR 상태를 다시 확인한다. 아래 로컬 상태는 2026년 10월 11일 확인값이다.
3. 사용자가 다음으로 진행할 일을 지정하면 그 범위부터 이어간다. 이전 작업의 미확인 상태를 완료로 간주하지 않는다.

새 세션 시작 메시지 예시:

> `docs/project-context.md`를 읽고 Mapmory 맥락을 이어받아줘. 문서 안의 날짜가 있는 상태는 최신인지 먼저 확인하고, 내가 이어서 할 작업을 말하면 이미 정리된 내용을 반복해서 묻지 말고 진행해줘.

## 제품과 홍보 방향

- Mapmory는 사용자가 지역을 검색해 선택하면 그 지역에 맞는 사진을 불러오고, 그중 원하는 사진만 골라 지역과 함께 여행 기록으로 남기는 서비스다.
- 첫 홍보의 우선 목표는 단순 도달이나 팔로워가 아니라 **앱을 설치하고 첫 기록을 저장하는 사용자**를 늘리는 것이다.
- 홍보물은 추상적인 지구본이나 일반 여행 사진만 보여주기보다 실제 앱 화면을 활용한다. 핵심 흐름인 `지역을 검색해 선택 → 해당 지역 사진 확인 → 사진 선택과 정리 → 기록 저장`이 한눈에 드러나야 한다.
- 이전 배너 시안에서는 실제 앱 화면을 사용한 구성이 선호됐다. 두 화면을 정렬하고 좌우 여백을 확보하는 수정 의견이 있었으며, 사진을 골라 정리해 기록으로 남기는 가치도 더 선명하게 보여주길 원했다.
- 상세한 앱 디자인 원칙은 [`DESIGN.md`](../DESIGN.md)를 기준으로 한다. 홍보물에서 실제 UI를 쓰더라도 앱과 다른 기능이나 화면을 만들어내지 않는다.

## 현재 홍보 채널 판단

- 사용자는 Instagram, Threads, DC Inside, LinkedIn, Telegram, Naver Cafe, Everytime 등 여러 채널을 검토하고 있다. 게시 전 각 커뮤니티의 자기홍보 규칙과 게시 조건을 확인해야 한다.
- Threads에서는 사진 정리 고민을 이야기할 때 반응이 있었지만, 앱 설치를 직접 권하면 반응이 떨어지고 설치로 이어지지 않는 경험을 공유했다.
- 사용자는 과거 Threads에 홍보성 글을 몇 차례 올린 뒤 계정 정지를 겪었다. 정지 알림의 구체적인 사유는 확인하지 않았으므로 홍보 자체가 원인이었다고 단정하지 않는다.
- 현재 판단은 Threads를 당분간 홍보 채널에서 보류하고, 같은 계정으로 홍보글을 반복 게시하지 않는 것이다. 계정 알림의 사유를 확인하기 전에는 정지 원인을 추측하거나 우회 방법을 제안하지 않는다.
- Instagram `@map_mory` 계정은 사용자의 계정이 아니며, 게시가 필요하면 계정 소유자에게 전달할 문안과 제작 지시를 정리한다. 사용자가 권한을 주지 않은 외부 계정에는 게시하지 않는다.
- Reels 음원으로 `The Process`를 찾던 중 검색 결과가 의도한 음원과 다르게 표시된 문제가 있었다. 정확한 음원을 확인하지 못했으므로 아티스트나 트렌드 음원을 확정해서 문서에 적지 않는다.
- 홍보 문안이나 전달 문서는 감성적인 카피보다 실행 가능한 지시 형식을 선호할 때가 있다. 예: `1. 음원은 ... 사용`, `2. 앱 화면은 ... 순서로 배치`.

## 스프린트 1 재제출, 비백엔드 맥락

2026년 10월 8일 팀 평가 캡처에서 스프린트 1 재제출 항목은 백엔드 3, 6, Android 1, 3, 제품 1, 2, 3, 4로 제시됐다. 사용자는 백엔드 항목은 제외하고 남은 일을 확인하고 있다. 백엔드 보완 항목은 이 사용자의 요청 범위에 넣지 않는다.

### Android, Crashlytics 증거

- 사용자가 제공한 문서 내용에 따르면 Crashlytics 연동 PR #288은 `develop`에 병합됐다.
- 사용자는 검증 크래시를 Google Play에서 다운로드한 앱에서 발생시켰다고 정정했다. 문서 초안의 검증 정보는 앱 `0.1.7`, `versionCode 9`, Firebase Console의 테스트용 크래시 보고서 수신이다.
- 이 크래시는 테스트용이며 실제 사용자 장애가 아니다. 새 세션에서 이 내용을 다시 다룬다면 사용자가 제공한 근거와 실제 Firebase/Play Console에서 새로 확인한 사실을 구분한다.
- 이전 로컬 저장소 문서에는 Sprint 2 개발자 도구 화면과 Android 계측 테스트의 런타임 제한이 기록되어 있다: [`docs/sprint-2/android-developer-tools.md`](sprint-2/android-developer-tools.md).

### 제품 1, 가설 검증 사이클

- 사용자가 앱을 보여주고 직접 사용하게 한 인터뷰 참여자 4명 중 3명이 기록 입력에 필요한 터치 횟수나 진행 단계가 많다고 말했다.
- 이에 기록 작성에서 직접 입력해야 하는 정보를 줄이면 시작 사용자 중 저장 완료 사용자 비율이 5%p 이상 오를 것이라는 가설을 세웠다.
- `5%p`는 인터뷰나 업계 통계에서 계산된 값이 아니다. 팀이 정한 최소 실무 개선 목표이며, 100명 중 완료자 5명이 늘어나는 변화를 판단 기준으로 삼았다.
- 팀 합의 자신감은 `8/10`이다. 이는 제품 가치와 유저를 모을 수 있다는 팀의 판단이지 가설이 검증됐다는 뜻이 아니다.
- 가설 판정은 **판정 불가**다. 변경 전후 기간과 표본이 다르고 과거 내부 QA가 포함되며 여러 변경 효과를 분리할 수 없다.
- 보고서에는 인터뷰 피드백이 문제 선택으로, 그 피드백을 줄이기 위한 기록 작성 변경이 다음 결정으로 이어졌음을 명시한다. 가설, 실험, 관측, 결론, 러닝, 다음 액션, 팀 합의 자신감을 한 사이클로 보여준다.

### 제품 3, 사용자 데이터 리포트

2026년 10월 10일 기준으로 사용자가 정리해 공유한 리포트의 핵심 값이다. 이는 사용자가 GA4에서 직접 조회해 전달한 수치이며, 이 세션에서 별도 계정 로그인으로 재조회한 값은 아니다.

- 활성 행동 정의: 7일 동안 `record_save_completed`를 1회 이상 발생시킨 고유 사용자.
- 여행 기록은 매일보다 여행 중이나 여행 후에 간헐적으로 쓰일 수 있어 DAU보다 WAU를 우선 관찰한다.
- 2026년 9월 17일–23일: 저장 완료 16회, 고유 사용자 6명.
- 2026년 9월 24일–30일: 저장 완료 14회, 고유 사용자 5명.
- 같은 GA4 기본 보고서의 활성 사용자 40명, 신규 사용자 31명은 기록 저장 기준 WAU가 아니므로 참고값으로만 구분한다.
- 과거 집계는 내부 QA 사용자를 외부 사용자와 분리하지 못했다. 사용자는 이 과거 데이터는 날것 그대로 두고 한계를 밝히며, 이후 집계부터 내부 QA를 구분했다고 설명했다. 과거 팀 밖 WAU를 억지로 계산하거나 이 불가피한 과거 한계를 미완료 액션으로 반복하지 않는다.
- W+1 코호트 조회값: `9/20–9/26` 4명 중 다음 주 1명, 25.0%; `9/27–10/3` 9명 중 다음 주 1명, 11.1%; `10/4–10/10` 4명은 다음 주 추적 전이라 미산출. 과거 QA 포함 여부는 코호트별로 새로 확인하지 않는 한 팀 밖 사용자 수치라고 표현하지 않는다.
- W+4는 기준일 당시 관측 기간 전이었다. 기준일 후의 현재 상태를 새 세션에서 물으면 오늘 날짜와 GA4를 다시 확인한다. 과거 기준 문서의 미관측 상태를 현재 상태로 그대로 옮기지 않는다.
- 리포트의 리텐션 그래프는 GA4 기본 그래프 원자료이고 `record_save_completed` 조건이나 과거 QA 제외 조건이 적용되지 않은 참고자료로 표기한다.
- 사용자는 보고서에 이미지 3장을 이미 넣었다고 확인했다: 기본 리텐션 그래프, `record_save_completed` 코호트 탐색 캡처, 작성 시작→저장 완료 퍼널 캡처. 이미지를 다시 만들거나 첨부하라고 요구하지 않는다.

### 제품 4, 핵심 지표

- 핵심 지표: 기록 작성을 시작한 고유 사용자 중 `record_save_completed`까지 도달한 고유 사용자의 비율.
- 시작 이벤트는 GA4 퍼널에서 `record_create_started`로 표기됐다.
- 사용자가 공유한 GA4 사용자 단위 퍼널 값:

| 플랫폼 | 구간 | 시작 사용자 | 저장 완료 사용자 | 전환율 |
|---|---|---:|---:|---:|
| Android | 변경 전 | 20 | 5 | 25.0% |
| Android | 변경 후 | 7 | 1 | 14.3% |
| iOS | 변경 전 | 22 | 9 | 40.9% |
| iOS | 변경 후 | 5 | 2 | 40.0% |
| 합계 | 변경 전 | 42 | 14 | 33.3% |
| 합계 | 변경 후 | 12 | 3 | 25.0% |

- 변경 전은 2026년 9월 3일–27일, 변경 후는 9월 28일–30일이다. 전체 전환율은 8.3%p 낮게 관찰됐다. 후 기간은 3일로 짧고, 과거 QA가 포함되어 있으므로 원인이나 개선 효과를 확정하지 않는다.
- 팀 목표는 기준선보다 5%p 높은 약 38.3% 이상이다. 5%p는 통계적으로 도출한 증명선이 아니라 팀의 최소 실무 판단 기준이다.
- 이전 초안의 “사용자 단위 퍼널 미측정” 문구는 위 퍼널 값이 추가된 뒤에는 최신 상태가 아니다. 새 세션에서 해당 문구를 재사용하지 않는다.

## 과거 엔지니어링 논의, 재개할 때 상태 확인 필요

아래는 긴 대화에서 있었던 작업 맥락이다. 현재 코드와 PR 상태는 이 문서만으로 보증되지 않는다.

- Android Studio는 새 창을 열지 말 것. 이미 열려 있는 `MapmoryClient` 창에서 프로젝트/브랜치만 전환한다.
- 작업은 `develop`에 직접 쌓지 않고 별도 브랜치에서 진행해 PR로 병합한다. 사용자가 요청한 경우 현재 열려 있는 Android Studio를 해당 브랜치로 전환한다.
- 장소 검색: 백엔드 API가 준비되어 있다고 공유됐고 Android UI 연결이 필요했다. 개발 서버에서 `판교`, `한강공원` 검색 결과가 화면에 안 나오거나 일반 오류 문구가 떴던 대화가 있었다. 현재 해결 여부는 저장소와 개발 서버 상태를 확인하기 전에는 단정하지 않는다.
- 개발 서버 로그인 만료 문제와 기존 기록 보존 문제가 있었다. 사용자는 서버를 수정하지 말라고 한 범위가 있었고, 앱의 로그인 연동은 백엔드 API 계약 보류 결정으로 미뤄둔 적이 있다. 인증 기능을 재개할 때는 그때의 범위를 먼저 확인한다.
- 사진 선택 화면에서 갤러리처럼 핀치 줌으로 열 수를 바꾸는 동작을 부드럽게 하고, 선택 사진만 기록에 남기는 UX와 버튼 문구를 다듬는 작업을 반복 요청했다. 현재 구현 상태와 PR #311 상태는 재확인한다.
- 독도와 대한민국 지도 경계, 특히 광주 경계와 독도 위치의 정확성이 중요하다고 했다. 지도 변경을 재개하면 임의 점 표시로 대체하지 말고 실제 경계 데이터와 검증을 확인한다.
- PR #321에 대해 DB 싱글톤 동시성, 캐시 JSON 파싱 fallback, SharedPreferences 저장, EXIF 날짜 파싱 관련 리뷰 의견을 검토하려고 했다. 해당 PR의 최신 상태는 다시 확인한다.

## 도구 사용 및 커뮤니케이션 선호

- 한국어 답변은 짧고 직접적으로, 결과와 현재 상태를 먼저 말한다. 불필요하게 긴 진행 멘트와 이미 정리한 사항의 반복을 피한다.
- 사용자가 이미 준 정보는 다시 묻지 않는다. 실제로 분기나 결과에 영향을 주는 정보가 빠졌을 때만 질문한다.
- 사용자가 검증을 요청하면 관련 화면, 코드, 데이터를 확인한 범위와 확인하지 못한 범위를 분리한다. 도구를 쓰지 않았는데 직접 확인했다고 말하지 않는다.
- 작성 문구에서는 가운데점 대신 쉼표 `,`를 쓴다. 정확한 원문 인용에서만 원문 표기를 유지한다.
- 외부 서비스 게시나 계정 변경은 사용자가 명시적으로 요청하고 계정 권한이 확인된 범위에서만 한다. 게시용 문안이나 전달 자료 작성과 실제 게시를 구분한다.
